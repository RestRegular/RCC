## 一、总体判断

§10 核心骨架自洽，能落到 Rio 现有模型：
- 任务只通过实参拿数据；
- 实参出生地包住 scope；
- 效果集按能力类型推导：Ref→R、Mut→W、Take→S；
- 共享可变只经二等值的 Locked，Atomic 视为只读。

本质是「把借用延伸到 scope 末尾」套在已有引用检查上，工程量可控。

主要风险不在检查器，而在三处：
1. **运行时地基**：分配器、TLS、异常、全局状态目前都是单线程假设。
2. **规范里的洞**：循环内 spawn、全局/外部调用、任务返回值、Chan 生命周期、happens-before。
3. **示例与正文不一致**：§10.8 的 `Take<Pool>`、`par_zip` 未定义。

## 二、逐节审视（缺口与矛盾）

### §10.1 / 10.2 作用域与任务
- **join 与 drop 顺序没定**。「出生地包住整个 scope」会把 scope 内新建局部变量排除在外，不能借给任务；若规定「隐式 join 先于 scope 体局部变量的 drop glue」可放宽。两种取法都合理（Q17）。
- **spawn 实参在哪个线程求值**：应在父线程求值（含 take 动作），子线程调用 → `s.spawn(f(args))` 应作特殊形式，而非普通表达式。
- **任务返回值完全没定义**：spawn 返回什么、有没有 join 句柄、结果如何回传（Q12）。
- **「不隐式捕获」≠「不碰外部状态」**：全局可变变量、`in global` 值、extern/FFI、stdout 都绕过「只通过实参获得数据」（Q13）。
- **并行组合检查三类遗漏**：
  - 父线程本身是一方：spawn 到 join 之间父线程代码也在并行跑，必须参与检查，否则父线程可在任务运行时随意读写借出的变量（§10.3 已隐含，但需明确）。
  - 循环内 spawn：同一 spawn 点产生多个任务，需「自己对自己」的检查；跨迭代的不等事实很难证明（Q4 子项）。
  - loop 内 take 循环不变量：第二轮会 take 一个已被 take 的值。
- **「join 后事实回到 ?」受事实表上限 256 影响**：只有内容被 Mut 改写的 slot 才需回到 ?，壳子状态只有被 take 的才变；否则大 scope 会冲掉大量事实。

### §10.3 并行组合检查
- **复杂度**：n 个 spawn 点做 O(n²) 两两检查，加父线程一方；§12 已列待实测，建议检查器先留计数钩子。
- **存储的 Ref**：Content 可含引用，`Ref<Foo>` 的读集合若不含「经 Foo 内存储的 Ref 间接读到的东西」就有洞。⚠需对照源码：单线程下「存储的 Ref 存活期间被指目标冻结」是只记出生地（寿命）还是也记独占性；若只记寿命，跨线程会出现一方持存储 Ref<Bar>、另一方拿 Mut<Bar>。
- **Link 与 Pool 的可达性**：`Ref<Pool<T>>` 读全部槽、`Mut<Pool<T>>` 写全部槽；效果代数需要「每个槽」全称路径，且要与实例级 `pool[i]` 路径冲突。⚠需对照 P13 路径词表。
- **「判断不了退回类型级并拒绝」安全但可用性有风险**：需好的诊断信息 + 测试证明常见写法能通过。

### §10.4 par_each
- **「Ref 捕获不能是同类型 T 的其他槽位，除非全程无写」基本等于禁止**：闭包参数是 Mut<T>，写 T 是常态，「全程无写」几乎不满足；建议改写为「不得捕获同一 Pool 或同类型 T 的 Ref」。
- **Link 遍历是漏洞**：规范只禁「调用 Link 原语」，但通过 Link 字段读邻居节点也是读别的槽，须同样禁止（除非 Link 读取本身不跨槽，需确认）。
- **par_each 阻塞性未定**：「阶段间由 scope join 分隔」暗示挂在外层 scope，但「每个槽恰好一次」需要知道它何时完成（Q18）。
- **receiver 能力**：元素可写、结构不可改，需要「只写元素」的 Pool 能力或路径。⚠需对照 §10.5 的 pool 级路径是否已分开「结构」与「元素」。
- **并发 add 与 par_each 交互**：§10.5 允许 add 与元素访问并行，但 par_each 需要稳定成员集合；迭代时是否快照？新 add 的槽是否可见？规范没说。

### §10.5 Pool 并发结构修改
- **`chunked(concurrent:true)` 是运行时参数，检查器需静态知道**：否则无法判断某 Pool 是否允许并发 add；要么变类型参数（新增类型/语法），要么编译期常量（Q16）。
- **chunk 目录自身增长**：「不搬动已有槽位」只保证 chunk 内容不动，没保证目录；句柄查找与目录增长会竞争。需确认目录是固定上限、分段目录还是 RCU 式替换。
- **release 总是独占**：效果应写明为 pool 级 S 加该槽的 W。

### §10.6 Locked / Atomic
- **解锁与异常**：lock 块内 return/break/异常时，解锁须在 unwind 路径执行（Q9 子项）；是否 poison 需裁决（Q6）。
- **同线程重入自死锁**：静态易检出，可做成错误而非 lint。
- **g 是二等值**，不能作为 spawn 实参（出生地规则本会拒绝），建议规则里写明。
- **Ref 只读公理被打破**：Locked/Atomic 允许通过 Ref 修改；写成通用「内部可变」标记还是写死三种类型，是语言设计问题（Q20）。
- **Atomic 后端**：需 lock xadd / lock cmpxchg / xchg 等指令，RCC 目前无对应 intrinsic，属「标准库公开接口 + 后端工作」。
- **Atomic 与非原子访问混用**：初始化与析构必须单线程，任务期间只能走原子操作。

### §10.7 通道
- **「Chan 是 Locked 的一种」不够**：阻塞 recv 需条件变量或 futex 等等待原语，互斥锁给不了，是运行时新增原语。
- **跨出生地所有权转移**：若出生地对应各自分配区域，send→recv 意味着 Content 及内部堆块换出生地；深拷贝还是所有权转移+重新归属，决定 Content 身份与代价。⚠需对照 P13 take 跨出生地语义。
- **Chan 关闭机制缺失**：「关闭为 null」但没说谁关、何时关；共享 Ref 无发送端计数，没人关则接收任务永远阻塞、scope 的 join 永远等。
- **容量（有界/无界）与背压未定义**（Q8）。
- **Msg 含 Ref 的约束须写进 Chan 类型约束**：来源出生地包住 scope 要在声明处就能检查。

### §10.8 粒子示例
- **`fn step(pool: Take<Pool<Particle>>, ...)` 很可疑**：Take 意味着消耗整个 Pool，函数末尾要返回或销毁；示例要的明显是「元素可写、结构不变」，应为 `Mut<Pool<Particle>>` 或「只写元素」能力。需确认是笔误还是有意（Q19）。
- **`par_zip` / `par_zip_into` 在 §10.4 没定义**：配对依据、into 是否创建 Force 槽、两 Pool 形状不变式都没说。
- **可能不需要 par_zip**：阶段1对 forces 做 par_each、捕获 `Ref<Pool<Particle>>` 用槽位 id 查；阶段2对 particles 做 par_each、捕获 `Ref<Pool<Force>>`。两阶段都落在 §10.4 允许的「捕获只读 Ref、类型不同」范围内。前提是要有「按槽位 id 只读查 Pool」接口，并确认该查找不构成对 T 的跨槽读。

### §10.9 竞争排除论证（建议补三条）
1. **happens-before 建立点须写明**：spawn、join、lock/unlock、send→recv、原子操作各自建立顺序；线程池实现需显式屏障。
2. **运行时库本身线程安全**：分配器、drop glue 释放、stdout、异常机制——现论证只针对用户数据，未覆盖运行时全局状态。
3. **环境访问**：全局变量与 extern 调用（Q13）。

## 三、跨章节前置条件

- **目标 OS/ABI 与运行时链接方式**：工作目录 D 盘推测为 Windows x64，但无证据；须确认链接 C 运行时还是裸系统调用，决定线程 API（CreateThread / pthread / clone）。
- **运行时全局状态审计**：逐项检查生成代码用到的全局可变状态（分配器、当前出生地栈、异常指针、drop 标志表、errno），决定哪些改 TLS（Windows 用 TEB/tls index）。**这是工作不是裁决**，建议作为 P14-1 第一个子任务。
- **drop glue 的线程归属**：take 进任务的值由任务线程析构，内存释放在与分配者不同的线程上，分配器必须允许。

## 五、对阶段路线的建议（供裁决）

1. **P14-1 拆分**：先做「P14-1a 运行时前置」（Q1、Q14、TLS、目标 ABI 确认、最小线程创建与 join 的 spike），再做「P14-1b scope/spawn」。
2. **P14-2 之前可让 spawn 串行执行**（在 join 处依次运行任务）验证检查器——静态无竞争的程序在任何交错下语义相同；含阻塞通信的用例不能这样测。
3. **测试策略**：需一套编译失败的负面用例覆盖每条拒绝规则，加多线程压力测试；自制编译器无法用现成 TSAN。
