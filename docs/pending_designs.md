## A. 值语义 `struct`（最高优先级）

### 为什么它是最高优先级

规范 §6.2 要求值语义 `struct`，而 Rio 现在**只有引用语义的 `class`**。
这不是"少一个语法糖"，是**语义空洞**：

```rio
class Player { var hp: int }
var a: Player = Player(100)
var b: Player = a        // 指针拷贝！a 和 b 指向同一对象
b.hp = 50
sout(a.hp)               // 50 —— 但内存模型要求这里必须是 100
```

`Content` 的唯一所有权前提是"赋值即转移"，而 `class` 的赋值是共享指针。
规范 §12 未决问题第 14 条已登记这个缺口，D19 裁决要求"正面引入值语义 struct 解决"。

**D19 的原话**：不采用"先做精简 P13-2、把用户对象推到后续子阶段"的方案，
P13-2 一次做完整版。所以这个不定，P13-2 就无法收尾。

### 规范怎么写的

`docs/memory-model-spec-full.md` §6.2 只有一句"值语义 struct"，
**没有任何语法**。实测 `struct Pt { var x: int }`：

```
Error: Code generation failed: Undefined variable: struct
```

### 我需要你定的（5 点）

1. **声明语法**。`struct Pt { var x: int }`？还是复用 `class` 加修饰符
   （`value class Pt`）？还是别的形态？

2. **与 `class` 的边界**。我的疑问是：如果 struct 和 class 语法几乎一样、
   只差一个关键字，用户凭什么判断该用哪个？是否需要显式的
   "只能装值类型字段"约束？继承要不要支持（我倾向**不支持**，值类型继承
   在布局上会退化成指针或切片，但这是你的设计权）？

3. **字段布局**。内联展开（`struct Pt { x: int, y: int }` 占 16 字节）是自然的，
   但**含 `str` 字段时怎么办**？`struct Name { s: str }` 里的 `s` 是指针，
   值拷贝时指针浅复制 = 两个 struct 共享同一个 `str` 头 —— 这违反值语义。
   需要定：禁止 struct 含引用类型字段？还是允许但标注"浅拷贝"？
   还是要求显式 `clone`？

4. **赋值语义**。`var b = a` 在 struct 上是**逐字节拷贝**还是**字段级移动**？
   如果是移动（a 之后不可用），那它就和 Content 移动没区别，值语义的意义
   就没了。我理解你要的是"可拷贝"，那么 `a` 拷贝后仍然可用 —— 但这与
   Content 唯一所有权**直接冲突**，需要你明确这个例外。

5. **与 Body/Content 状态格的关系**。struct 是 Content 的一种吗？
   `var s: Pt = ...` 时 `s` 进不进移动状态表？`&s` 得到的是 `Ref[Pt]`
   还是展开成 `Ref[int]`（子引用）？

### 我的建议（供参考，不是方案）

最小可行版本：`struct` 只允许**标量字段**（int/float/bool/char/ptr），
不支持继承、不支持引用类型字段、赋值即逐字节拷贝、不进 Content 状态格
（当作和 `int` 同级的"纯值类型"）。这样 D19 要的"class 指针拷贝与 Content
唯一所有权的冲突"就有了出口：需要值语义的场合改用 struct。
含 `str` 字段的需求等 P13-4 有了元素级 clone 再说。

## B. `Maybe` / `if let` / `match` 窄化（最高优先级）

### 规范怎么写的

§3.4 / §8.2 写的是 `get()?.name`、`if let Some(p)`、`match`。
但**语法全是示意**（规范第 4 行自己标注了"语法为示意，未最终确定"）。

### 现状实测

```rio
class P { var n: str }
var a: P? = P("x")
if let b = a { sout(b.n) }
```
```
Error: Compilation failed: syntax errors.
```

`if let` / `match` 两个关键字都不存在。`T?` 类型本身存在（P12 已有）。

### 已有裁决的约束（这部分不用你重定）

- 裁决 `388a73e0`：**只有引用类型可空** + 对象包装基本类型
- 裁决 `a87037d8`：零值方案（用 null 表示"无"）**不可行**，已证伪
- 决议 §16.2：倾向 `get()` 返回 `T?`，**不引入 Maybe** —— 但标注"未最终确认"

### 我需要你定的（4 点）

1. **到底引不引入 `Maybe` 类型？** 决议倾向"不引入、复用 `T?`"，
   但 `T?` 只能表达"引用为空"，表达不了"计算出错"。
   `get()` 越界是返回 `T?`（null）还是 panic？这两个语义完全不同。

2. **`if let` 的语法**。`if let b = a { }`？还是 `if b = a? { }`？
   还是别的？规范里的 `Some(p)` 形态依赖 Maybe 存在，如果不定 Maybe，
   这个形态就用不了。

3. **`match` 的语法与范围**。完整模式匹配（含字面量、范围、守卫）
   还是只做"可空/错误两分支"？完整 match 是一个大特性，
   我不确定你是否想在这个阶段引入。

4. **与现有 `T?` 的关系**。`T?` 现在是"可空引用"，如果引入 Maybe，
   两者是并存还是 `T?` 变成 `Maybe[T]` 的语法糖？后者是 Breaking。

### 我的建议

如果目标只是"安全地取出可空值"，最小方案是只加 `if let`，
不引入 `Maybe`、不做 `match`。`get()` 越界 panic（与 `[i]` 越界 panic 一致），
"可能失败"用 `T?` 表达。这样 §8.2 的窄化需求基本满足，
且不动 `T?` 的现有语义。

## C. 条件销毁的诊断级别

### 规范怎么写的

§8.4 第 3 点：分支出口状态不一致时插条件销毁（flag 位图），
默认**警告**，模块级 `#[strict_destroy]` 升级为**错误**。

### 现状

条件销毁的**代码生成**已经能工作（实测 `f4_cond_run` 正常输出），
但"警告/错误"这一层诊断**没有实现** —— 现在既不警告也不报错。

### 我需要你定的（2 点）

1. **属性语法形态**。`#[strict_destroy]` 这个写法是示意，Rio 现在
   **没有属性语法**（`#` 在 Rio 里连注释都不是，实测会当代码解析）。
   模块级属性加在哪？文件头？还是 `module` 声明上？

2. **默认级别**。真的默认警告吗？考虑这个场景：

```rio
var s: str = "x"
if cond { s = "a" }
// 出口处 s 可能是 "x" 也可能是 "a"，需要条件销毁
```

   如果每个这种正常写法都警告，警告会非常多。我倾向**默认静默**
   （就像现在这样），只保留 `#[strict_destroy]` 选项让用户主动开启。
   但这与规范写的"默认警告"不符，需要你裁决。

## D. `split(k)` 两段视图的绑定形态

### 规范怎么写的

§4.3 只写"返回两段 Mut 视图"，**没说怎么绑定**。

### 现状实测

```rio
var xs: list[int] = [1,2,3]
var parts = xs.split(1)
```
```
Error: Cannot determine the object type of method call
```

方法存在性都判定不了，因为返回类型未定。

### 我需要你定的（3 点）

1. **两段怎么返回**。元组 `var (a, b) = xs.split(1)`？数组
   `var ps = xs.split(1); ps[0]`？还是**调两次**
   （`xs.split_at(1)` 和 `xs.split_from(1)`）？

   Rio 现在**没有元组**（我确认过），所以第一个选项意味着要先加元组 ——
   那是个大特性。我倾向第三个选项（调两次），零新语法。

2. **越界语义**。`split(5)` 在 3 元素列表上怎么办？panic？返回空？

3. **视图的失效规则**。两段 Mut 视图存活期间，原列表能做什么？
   决议 §4.1 有前缀冲突规则，但"两段视图同时存在"是否合法
   （它们不重叠，理论上可以）需要明确。

### 我的建议

调两次（`split_at` / `split_from`），零新语法，且天然避开"元组不存在"的问题。
越界 panic（与索引一致）。

### 现状

`throw` 创建的对象永远泄漏（D1 裁决"异常即泄漏"）。这在 P13-1/P13-2

长期看，异常对象归谁管？catch 之后由 catch 块销毁？还是进程级池？

## 9. 一句话总结

**真正挡路的只有两件：值语义 `struct` 和 `Maybe`/`if let` 窄化。**
