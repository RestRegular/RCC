## 1. 为什么地基必须先做

### 1.1 当前状态：完全没有生命周期管理（实测）

| 事实 | 证据 |
|---|---|
| 没有任何析构机制 | `git grep -n "destructor\|dtor\|emitDestroy\|releaseScope\|dropScope\|cleanupScope\|leaveScope\|scopeExit" -- code/` **零命中** |
| `emitBlock` 只弹符号表 | `rcc_codegen.cpp:2536-2538` 只有 `pushScope()` / `popScope()`，不生成任何释放代码 |
| `core_free` 从未被调用 | 全仓只在 `rcc_codegen.cpp:1344` 的白名单字符串里出现；`lib/std/ds.rio:76` 明写「本模块不调用 core_free」 |
| 容器只分配不释放 | `list`/`dict` 每个都是 `core_alloc` 一次，永不回收 |

**后果**：长驻进程反复分配容器会持续增长；这不是「优化没做」，是「机制不存在」。

### 1.2 三个延期项全部以地基为前提

| 延期项 | 出处 | 为什么卡在地基上 |
|---|---|---|
| **G6** 闭包捕获写回 | `p12_plan.md` §10.2 | 写回要求「闭包与外层共享同一个槽位」，而槽位身份、出生地、销毁点正是地基内容。没有地基就写 boxed cell 是与未来方案冲突的临时方案 |
| **G1b** argv 通道 | §10.2 | 规范空白 Q9：启动期 argv 的**出生地归属**未定（`in global`？`in result`？）。出生地是地基概念 |
| **容器生命周期语义** | `p12_plan.md` §10.2、§5.6 | `listAppend` 为何返回新列表、`copy` 为何只能浅拷贝、`release` 为何不可用——全都等「销毁点如何生成」定稿 |

### 1.3 继续往后做的代价

变长参数（设计已批、9 项清单）打包成 `list[T]`，会**加深**对「容器引用语义」的依赖。
地基未定时先做它，等于在未定稿的容器语义上再压一层，将来返工面更大。这是用户选「先打地基」的实质理由。

## 2. 规范与现状的差距（必须先摆清楚）

### 2.1 规范里的概念，语言里**一个都没有**（实测）

```
git grep -n "Ref<\|Mut<\|Take<\|Body\.\|Content\.\|Pool\.\|Link<" -- lib/std/ lib/core/   → 零命中
git grep -n "in local\|in result\|in pool" -- code/ lib/                                → 零命中
```

规范要求而当前语言不存在的：

| 规范概念 | 规范出处 | 当前状态 |
|---|---|---|
| `Body<T>` / `Content<T>` 双所有者 | §2.1 | 无 |
| 出生地 `in local` / `in result` / `in pool` | §2.2 | 无 |
| 能力类型 `Ref<T>` / `Mut<T>` / `Take<T>` | §3.2 | 无（`any` 是「指针族值」，不是能力类型） |
| 子引用与路径登记 | §4 | 无（索引写有边界检查，但没有「活跃子引用」概念） |
| 签名标注 `from` / `writes` / `ensures` | §5 | 无 |
| `Pool` 与成员集合追踪 | §6 | 无 |
| `Link<T, dual, 基数>` | §7 | 无 |
| 状态格 F/E/`?`、H/X、窄化 | §8 | 无 |
| 结构化并发 `scope` / `spawn` | §10 | 无 |

**结论**：这不是「补几个函数」，是把整套所有权系统建起来。必须分阶段。

### 2.2 规范与现状的**直接冲突**：异常

| | 规范 §9 | 当前语言 |
|---|---|---|
| 异常 | 「**没有展开（unwinding）。语言里没有异常。**」 | **有** `try`/`catch`/`finally`/`throw`，P7 已实现并验收（`test_p7_exceptions.ps1` 17/17） |
| 实现方式 | — | 显式帧链（setjmp/longjmp 风格），`core_panic_raise` 在 `core_win64.s:408` |
| 不可恢复失败 | `abort()` 直接终止，不运行任何销毁 | `core_proc_exit` |

规范 §9 自己标了 **【待确认】**：「这是 v0.3 里替你暂定的取舍。」

**这是 P13 的第一个必须裁决的问题**，因为它决定「每条路径每个所有者恰好销毁一次」这条
不变量能不能成立：有展开就必须考虑异常路径上的销毁；无展开只需考虑正常控制流出口。

### 2.3 规范自身的待确认与未决

- 正文 **2 处【待确认】**（实测：L519 = §9 无展开的取舍；L794 = §12 第 1 条重述同一件事。
  两处指向**同一个问题**，即 D1）
- **14 条未决问题**（§12，实测计数），其中影响地基的有：Q9 出生地归属、Q11 `trust` 块治理、
  Q12 容器元素路径、Q13 跨模块签名兼容、Q14 条件销毁诊断边界
- 并发（§10）整章是「首版构想」，与内存安全地基可分阶段解耦

## 4. 需要用户裁决的问题（D1–D8）

> 这些是 P13-1 开工前必须定死的。每条给出选项与我的推荐，但**推荐不等于已批准**。

### D1【最关键】异常与析构的关系

规范 §9 说「没有异常」，但语言已有 try/catch/finally/throw 并已验收。

| 选项 | 含义 | 后果 |
|---|---|---|
| **A. 保留异常，析构在异常路径上不保证** | 异常展开时不运行销毁，等价于「异常即泄漏」 | 实现简单；但「每个所有者恰好销毁一次」只在正常路径成立，规范 §9 的不变量要改写 |
| **B. 保留异常，展开时运行析构** | 需要 unwind 表或帧链上挂销毁回调 | 与「无隐式行为」原则冲突（§1 目标 2），状态分析复杂度大增 |
| **C. 移除异常，改用 `Result`/`Maybe`** | 与规范 §9 一致 | 但这是**删除已有语言特性**，属 Breaking，需你明确批准；且 `test_p7_exceptions.ps1` 17 项要重写 |

**我的推荐：A**。理由：异常是 P7 已验收的既成事实，移除代价大且与「不为历史兼容性制造技术负担」
的原则不矛盾（它是在用特性，不是历史包袱）；而「展开时运行析构」与规范的核心原则（无隐式行为）直接冲突。
选 A 只需把规范 §9 的不变量从「每条路径」收窄为「每条正常控制流路径」，并把「异常即泄漏」写进文档。

### D2 P13-1 是否只做「值都是 Content」

用户已给的边界是「值都是 Content，不引入 Body」。确认这一条是否仍成立？
若成立，P13-1 不需要 `Body<T>` 语法，工作量小很多。

**我的理解：成立**（依据记忆 `00ea3674` 的记录）。需要你确认，因为它直接决定 P13-1 的范围。

### D3 `in local` / `in result` 的语法形态

规范写 `let a = Body.new(...) in local`。当前语言用 `var` 而非 `let`，且没有 `in` 关键字用作出生地。

| 选项 | 写法 |
|---|---|
| **A. 绑定处后缀** | `var a: list[int] in local = [1,2,3]` |
| **B. 表达式后缀** | `var a = [1,2,3] in local` |
| **C. 不引入语法，靠推断** | 所有局部变量默认 `in local`，只对 `result` 显式标注 |

**我的推荐：C 起步，逐步加 A**。理由：当前所有局部变量本来就是「作用域末销毁」语义，
默认 `in local` 不需要任何语法；只有 `in result`（返回值转移）和 `in pool` 才需要显式写。
这样 P13-1 可以**零语法改动**起步，把语法决策推到真正需要时。

### D4 销毁代码的生成位置

| 选项 | 做法 |
|---|---|
| **A. 每个出口显式插销毁** | 按规范 §2.4，`break`/`continue`/`ret`/作用域末各插一份 |
| **B. 统一跳转到 epilogue** | 函数级单一销毁段，各出口跳到它 |
| **C. 循环内每轮销毁** | 循环体作用域末插销毁 |

**我的推荐：A + C**（即规范的写法）。B 更省代码体积但与「按当前状态插销毁」冲突（不同出口状态不同）。

### D5 `core_free` 的失败语义

`core_free(nullptr)` 是否安全？重复释放如何处理？

**我的推荐**：`core_free(nullptr)` 静默返回（与 `core_str_len(null)=0` 一致）；
重复释放是**未定义行为**，不加运行期检查（符合「无隐式运行时检查」原则）。
需要你在 P13-1 前确认，因为 `list` 的递归释放会大量遇到空指针。

### D6 `listAppend` 改回原地追加的时机

当前 `listAppend` 返回新列表，原因是「索引写有边界检查，手工改长度头后 `xs[n]=v` 仍被跳过」
（`p12_plan.md` §10.2 实测）。

| 选项 | 时机 |
|---|---|
| **A. P13-1 一起改** | 与销毁机制同时落地，因为原地追加要改长度头，与生命周期管理是同一套 |
| **B. 等 P13-2** | 先保留返回新列表 |

**我的推荐：A**。理由：原地追加的核心障碍是「codegen 的边界检查不认手工改的长度」，
这需要 codegen 提供受控接口（如内建 `core_list_append`），属于同一层改动。

### D7 是否接受「P13-1 期间 `test_14/15` 仍失败」

G6 依赖 P13-3，P13-1 完成时 `test_14_iter` / `test_15_forinrange` 仍会失败。

**我的推荐：接受**，维持 P12 的口径：不改 `expected.txt`，标注「G6 延期」。
需要你确认 P13-1 的验收门槛不含这两项。

### D8 并发（§10）是否纳入 P13

| 选项 | 后果 |
|---|---|
| **A. 不纳入，留 P14** | P13 专注内存安全地基，范围可控 |
| **B. 纳入 P13-8** | P13 会显著变长，且并发依赖前面全部完成 |

**我的推荐：A**。理由：规范 §10 自己说「首版构想」，且有 4 条未决问题（Q2/Q3/Q5/Q6）直接涉及并发。

## 5. 待审批的语法提案（P13-1 用）

> 按项目硬规则，以下全部是**提案**，未获批不得实施。

### 5.1 出生地语法（对应 D3）

**提案 S1（推荐）**：不新增局部变量语法，只对返回值转移显式标注。

```rio
// 局部变量：默认 in local，无需标注
var xs: list[int] = [1, 2, 3]        // 作用域末销毁

// 返回值：显式标注转移
fun make(): list[int] {
    var xs: list[int] = [1, 2, 3]
    ret xs in result                  // 所有权转交给调用者
}
```

若 S1 获批，P13-1 **零语法改动**（`in result` 只是 `ret` 的可选后缀）。

**备选 S1'**：`var xs in local = ...` 显式写出生地（规范原文风格，但更啰嗦）。

### 5.2 Body/Content 语法（P13-2 用，此处只登记）

规范写 `Body.new(...)` / `Content.new(...) in result`。
**P13-1 不需要，P13-2 前单独提案。**

### 5.3 能力类型语法（P13-3 用，此处只登记）

规范写 `Ref<T>` / `Mut<T>` / `Take<T>`、`f(take x)`、`r.get()?.name`。
