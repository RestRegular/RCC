## 1. 为什么地基必须先做

### 1.1 当前状态：完全没有生命周期管理（实测）

| 事实 | 证据 |
|---|---|
| 没有任何析构机制 | `git grep -n "destructor\|dtor\|emitDestroy\|releaseScope\|dropScope\|cleanupScope\|leaveScope\|scopeExit" -- code/` **零命中** |
| `emitBlock` 只弹符号表 | `rcc_codegen.cpp:2536-2538` 只有 `pushScope()` / `popScope()`，不生成任何释放代码 |
| `core_free` 从未被调用 | 全仓只在 `rcc_codegen.cpp:1344` 的白名单字符串里出现；`lib/std/ds.rio:76` 明写「本模块不调用 core_free」 |
| 容器只分配不释放 | `list`/`dict` 每个都是 `core_alloc` 一次，永不回收 |

**后果**：长驻进程反复分配容器会持续增长；这不是「优化没做」，是「机制不存在」。

### 1.2 三个延期项全部以地基为前提

| 延期项 | 出处 | 为什么卡在地基上 |
|---|---|---|
| **G6** 闭包捕获写回 | `p12_plan.md` §10.2 | 写回要求「闭包与外层共享同一个槽位」，而槽位身份、出生地、销毁点正是地基内容。没有地基就写 boxed cell 是与未来方案冲突的临时方案 |
| **G1b** argv 通道 | §10.2 | 规范空白 Q9：启动期 argv 的**出生地归属**未定（`in global`？`in result`？）。出生地是地基概念 |
| **容器生命周期语义** | `p12_plan.md` §10.2、§5.6 | `listAppend` 为何返回新列表、`copy` 为何只能浅拷贝、`release` 为何不可用——全都等「销毁点如何生成」定稿 |

### 1.3 继续往后做的代价

变长参数（设计已批、9 项清单）打包成 `list[T]`，会**加深**对「容器引用语义」的依赖。
地基未定时先做它，等于在未定稿的容器语义上再压一层，将来返工面更大。这是用户选「先打地基」的实质理由。

## 2. 规范与现状的差距（必须先摆清楚）

### 2.1 规范里的概念，语言里**一个都没有**（实测）

```
git grep -n "Ref<\|Mut<\|Take<\|Body\.\|Content\.\|Pool\.\|Link<" -- lib/std/ lib/core/   → 零命中
git grep -n "in local\|in result\|in pool" -- code/ lib/                                → 零命中
```

规范要求而当前语言不存在的：

| 规范概念 | 规范出处 | 当前状态 |
|---|---|---|
| `Body<T>` / `Content<T>` 双所有者 | §2.1 | 无 |
| 出生地 `in local` / `in result` / `in pool` | §2.2 | 无 |
| 能力类型 `Ref<T>` / `Mut<T>` / `Take<T>` | §3.2 | 无（`any` 是「指针族值」，不是能力类型） |
| 子引用与路径登记 | §4 | 无（索引写有边界检查，但没有「活跃子引用」概念） |
| 签名标注 `from` / `writes` / `ensures` | §5 | 无 |
| `Pool` 与成员集合追踪 | §6 | 无 |
| `Link<T, dual, 基数>` | §7 | 无 |
| 状态格 F/E/`?`、H/X、窄化 | §8 | 无 |
| 结构化并发 `scope` / `spawn` | §10 | 无 |

**结论**：这不是「补几个函数」，是把整套所有权系统建起来。必须分阶段。

### 2.2 规范与现状的**直接冲突**：异常（已裁决，D1）

| | 规范 §9（原稿） | 当前语言 |
|---|---|---|
| 异常 | 「**没有展开（unwinding）。语言里没有异常。**」 | **有** `try`/`catch`/`finally`/`throw`，P7 已实现并验收（`test_p7_exceptions.ps1` 17/17） |
| 实现方式 | — | 显式帧链（setjmp/longjmp 风格） |
| 不可恢复失败 | `abort()` 直接终止，不运行任何销毁 | `core_proc_exit` |

规范 §9 原稿自己标了 **【待确认】**：「这是 v0.3 里替你暂定的取舍。」
这决定「每条路径每个所有者恰好销毁一次」这条不变量能不能成立，所以是 P13 的第一个必裁项。

**已裁决：D1 = A** —— 保留异常，异常路径**不保证**销毁（异常即泄漏），并配 D13 的
「`catch` 入口状态取合并 / P13-1 禁止在 `try` 体内移动外层拥有者」防止它变成双重释放。
规范 §9 已据此**全面重写**，那条【待确认】已消除。裁决细节见 §4 的 D1 与 D13。

### P13-1：最小可用地基（只有内置类型，Body 隐式）

这是**唯一一个必须先定死范围**的阶段。用户 2026-11-17 已给出阶段 1 的验收边界
（见记忆 `00ea3674`），并按 D15 修正了 Body/Content 的表述：

| 边界 | 内容 |
|---|---|
| 类型范围 | **只有内置类型**（`int`/`float`/`bool`/`str`/`char`/`list`/`dict`），无用户类 |
| 值的身份 | 堆块是 **Content**；局部变量这个「槽位」是 **Body，但隐式**——恒为 Full，没有语法、没有 F/E 状态，只追踪 H/X（D15） |
| 出生地 | 只需 `local` / `result` 两档；两者都**不写语法**，靠推断（D3 选 C） |
| 销毁代码 | 按**元素类型**编译期生成 drop glue，无运行期类型分派（D16） |
| 引用 | 只作**参数传递和临时子引用**，不存储 |
| 子引用路径 | 只需 `items` / `items[*]` 两档 |
| 状态格 | 只需 H / X 两档 |
| 别名 | 统一按 D9 的规则 C：新值初始化 = 拥有者，已有变量/元素初始化 = 借用 |

**产出**：
1. 作用域末销毁代码生成（`emitBlock` 的 `popScope` 处插销毁，顺序为声明逆序）
2. 表达式临时值在**语句末**销毁（D10：临时值 = 出生地为当前语句的匿名 local）
3. `core_free` 接通（含 `list`/`dict`/`str` 的递归释放）
4. `core_free` 的两条静默返回：`nullptr` 与 `cap == 0`（字面量静态头，D11 选 A）
5. `listAppend` 改回**原地追加**，前置条件是 `list`/`dict` 的 **header 与 data 分离**（D12 选 A）
6. `copy` 升级为 `clone()` 深拷贝
7. **移除 `rc` 字段**，与第 5 项合并为一次 **ABI v2**（不拆成两次改 ABI）
8. `for` 遍历某变量期间，禁止对该变量调用 `listAppend` / `listRemove` / `dictRemove`
   （D6 + D12 的配套保守规则，P13-4 再放宽）
9. 调试构建钩子：分配/释放计数、释放后填 `0xDD`、重复释放检测（D17）
10. 回归脚本 `test_scripts/test_p13_memory.ps1`（含 D18 的四类负向用例）

**验收**：
- `xs` 作用域结束后 `core_free` 确实被调用（用产出 9 的计数器验证）
- 容器在作用域末释放自身的 header + data，无重复释放。**元素不递归释放**
  （D14 已裁决：判定元素所有权要等 P13-4 的子引用路径），所以
  `list[list[int]]` 的内层两块是**已知泄漏**，由回归用例锁定这个数字 ——
  哪天内层也被释放了，`dictKeys` / 浅拷贝那批场景就会开始 use-after-free
- 四类负向用例必须**编译报错**且带 `file:line:col`：使用已移动的值、返回借用的形参、
  存储借用、在 `try` 体内移动外层拥有者（D13）
- `test_14_iter` / `test_15_forinrange` **不变**（G6 仍延期，不靠改预期制造通过）

### P13-1 明确不覆盖（D14）

`class` 实例、`any`、`func` 的闭包 env 一律**不释放**（它们是引用语义，直接释放必是双重释放）；
`list[Foo]` 只释放缓冲区，不释放元素。这些等 P13-2 的 Body 概念定稿后再处理。

### P13-2：Body / Content 双所有者 + 出生地三档

**范围裁决（2026-11-17 用户确认）**：**突破 P13-1 的「只有内置类型」边界，P13-2 一次做完整版** ——
值语义 `struct` + `Maybe` / `if let` / `match` 窄化 + 全套 F/E 状态格 + 条件销毁 +
`in pool` 全部在本阶段落地。不采用「先做精简 P13-2、把用户对象推到后续子阶段」
的方案。这意味着 D19 的前置缺口（值语义结构体从哪来）通过**正面引入值语义 struct**
解决；原先「阶段 1 只有内置类型」的边界只约束 P13-1，不再约束 P13-2。

| 项 | 内容 |
|---|---|
| 新增概念 | `Body<T>`、`Content<T>`、`in pool`、值语义 `struct`、`Maybe` |
| 语法 | **待用户提供设计文档后逐条裁决**（见下方「设计未决」）；此处不预先写死任何语法形态 |

| 销毁 | 每个出口按当前状态插销毁；合流不一致时条件销毁（flag 位图，§6.5） |
| 验收 | §8.7 的出口规则、§8.4 的目的地传递 |
| **D19 处置** | 已裁决：正面引入值语义 `struct` 解决 `class` 指针拷贝与 Content 唯一所有权的冲突。具体语法设计见「设计未决」 |

### D1【最关键】异常与析构的关系

规范 §9 说「没有异常」，但语言已有 try/catch/finally/throw 并已验收。

| 选项 | 含义 | 后果 |
|---|---|---|
| **A. 保留异常，析构在异常路径上不保证** | 异常展开时不运行销毁，等价于「异常即泄漏」 | 实现简单；但「每个所有者恰好销毁一次」只在正常路径成立，规范 §9 的不变量要改写 |
| **B. 保留异常，展开时运行析构** | 需要 unwind 表或帧链上挂销毁回调 | 与「无隐式行为」原则冲突（§1 目标 2），状态分析复杂度大增 |

**我的推荐：A**。理由：异常是 P7 已验收的既成事实，移除代价大且与「不为历史兼容性制造技术负担」
的原则不矛盾（它是在用特性，不是历史包袱）；而「展开时运行析构」与规范的核心原则（无隐式行为）直接冲突。
选 A 只需把规范 §9 的不变量从「每条路径」收窄为「每条正常控制流路径」，并把「异常即泄漏」写进文档。

**裁决：A。** 但**必须带上 D13 的配套规则**——否则「异常即泄漏」会变成「异常即双重释放」
（try 体内已消耗的外层所有者，catch 之后在作用域末会再释放一次）。规范 §9 已按此改写。

### D3 `in local` / `in result` 的语法形态

规范写 `let a = Body.new(...) in local`。当前语言用 `var` 而非 `let`，且没有 `in` 关键字用作出生地。

| 选项 | 写法 |
|---|---|
| **A. 绑定处后缀** | `var a: list[int] in local = [1,2,3]` |
| **B. 表达式后缀** | `var a = [1,2,3] in local` |
| **C. 不引入语法，靠推断** | 所有局部变量默认 `in local`，只对 `result` 显式标注 |

**我的推荐：C 起步，逐步加 A**。理由：当前所有局部变量本来就是「作用域末销毁」语义，
默认 `in local` 不需要任何语法；只有 `in result`（返回值转移）和 `in pool` 才需要显式写。
这样 P13-1 可以**零语法改动**起步，把语法决策推到真正需要时。

**裁决：C。** 分阶段口径（用户 2026-11-17 确认）：

| 阶段 | Body 出生地 | 临时值出生地 | 语法 |
|---|---|---|---|
| P13-1 | 隐式，恒为 `local` | 隐式，语句级匿名 `local` | **零新增语法** |
| P13-2 起 | **永远显式**写 `in local` / `in pool` / `in result` | 位置可推出时省略，Body 仍显式 | 按 §5.2 单独提案 |

### D9 别名与所有权规则

**选项**

| 选项 | 含义 |
|---|---|
| A. 赋值即移动 | 源变量变 X，再使用报错 |
| B. 赋值即深拷贝 | 全部拷贝，没有别名 |
| **C. 按初始化表达式判定所有权** | 见下 |

**规则 C**（P13-1 采用）：

| 初始化表达式 | 该变量的性质 |
|---|---|
| 新值（字面量、函数调用结果、`clone()`） | **拥有者**，作用域末销毁 |
| 已有变量或元素（`var ys = xs`、`xs[0]`） | **借用**，不销毁 |
| 形参 | 一律**借用**；被调函数不释放，调用方负责 |

借用**不能** `ret`、不能存进容器、不能赋给外层作用域的变量、不能被会逃逸的闭包捕获，
违反时编译报错。拥有者作为整体 `ret` 或存入容器时发生**移动**，源变为 X，之后使用报错
—— 这就是 H/X 两档在 P13-1 里的全部用途。对拥有者重新赋值时：先算右值，再释放旧值，再写入。

**裁决：以用户在 D9 给出的模型总纲为准**，规则 C 是它在「没有能力类型」阶段的编译期近似：

> 这门语言把「对象」拆成壳子（Body）与内容（Content）两个所有者：壳子在创建时用
> `in local` / `in pool` / `in result` 显式指定出生地，之后永不搬家，销毁点就是出生地的结束处，
> 所以引用指向的地址稳定；内容可以被 `take` 出来、转移、重新填充，但同样必须有出生地和
> 编译期确定的销毁点，转移语义是「消耗旧的、在新出生地创建新的」，因此 **Content 不能被引用、
> 也不存在别名**。引用只指向壳子，分 `Ref`（读）、`Mut`（改字段）、`Take`（取出与填入，独占）
> 三种能力，可降级不可升级，**允许任意别名**；安全性不靠禁止别名，而靠两条规则：
> 一是**局部排他**（任何可能使内存失效的操作只需保证没有与之路径重叠的活跃子引用，且函数的
> 写效果按「类型.字段」级别记录，堵住通过存储引用修改被迭代容器的漏洞）；
> 二是**状态跟踪**（编译器对每个槽位追踪 Full / Empty / 不确定，确定 Full 直接访问、
> 确定 Empty 编译拒绝、不确定时必须显式写 `get()`，因此语言里没有任何隐式的运行时检查或终止）。
> 容器作为出生地时用分块等稳定地址结构，`release` 槽位要求无任何活跃引用，由成员集合追踪证明；
> 图、双向链表这类互指结构只提供一个原语 `Link<T, 对偶字段, 基数>`，成对修改并维护
> 「对端必为 Full」的不变量；`from` / `writes` / `ensures` 一律「缺省保守、只用于放宽、函数体被验证」。
> 当前明确搁置：并发，以及结构体字段内子引用的路径精度。

P13-1 里 `var ys = xs` 解释为「**对 `xs` 壳子的隐式引用**」，规则 C 到 P13-3 被
`Ref`/`Mut`/`Take` 取代。

### D10 表达式临时值的生命周期

**问题是**：规范里每个值都有出生地，但没有「表达式临时值」这个概念。
`"a" + b + "c"` 会产生中间 `str`，`sout(make())` 会产生返回的 `list`，`make();` 的结果被直接丢弃
—— 谁来释放？不处理的话 P13-1 对 `str` 基本没有实际效果，因为大部分分配都来自临时值。

**裁决：临时值不是新概念，它是「出生地为当前语句的匿名 local」，销毁点 = 语句末尾。**
`in ...` 标注里，Content 的出生地可由位置推出时可省略，**Body 永远显式**（P13-2 起；P13-1 见 D3 分阶段口径）。

P13-1 的落地方式：每条语句维护一个临时值表，语句结束时销毁其中**未被移走**的。
新值被绑定、`ret` 或存入容器时从临时表移走，其余在语句末释放。

### D11 `str` 字面量与 `core_free`

**问题是**：架构文档 §4.2 规定字面量指向静态只读 header、`cap=0`。对静态 header 调 `core_free`
会直接崩；同理 `fun name(): str { ret "abc" }` 返回的是静态指针，调用方会把它当成自己拥有的。

| 选项 | 含义 |
|---|---|
| **A. `core_free` 对 `cap==0` 的 header 静默返回** | 字面量不拷贝 |
| B. 绑定时复制字面量 | 每个字面量一次堆分配 |

**裁决：A。** 理由：B 会让每个字面量都变成堆分配，与架构文档「字面量零分配」的设计冲突；
A 是对**值表示的约定**（`cap==0` 即不可释放），不是隐式运行时检查，只需文档化。
D5 一并扩写为「`nullptr` 静默返回 / `cap==0` 静默返回 / 重复释放是未定义行为」。

### D12 原地追加的布局问题（D6 的前提）

**问题是**：现在 `list` 是单指针指向 `header + data[]`，原地追加遇到扩容就要 `realloc`，
此时调用者的变量、其他拷贝、形参里的指针**全部失效**。
`fun add(l: list[int]) { listAppend(l, 1) }` 改的只是被调用方的局部槽位。

| 选项 | 含义 |
|---|---|
| **A. header 与 data 分离** | header 地址永不变，data 可 `realloc` |
| B. `listAppend` 做成左值内建，写回变量槽位 | 保持单指针 |
| C. 等 P13-3 的 `Mut` | D6 改为推迟 |

**裁决：A。** 理由：

- B 解决不了形参 —— 写回的是被调用方自己的槽位，调用方的变量不变。结合 D9「形参是借用」，
  必须让别名之间共享同一个**稳定的 header**。
- A 与规范 §2.3「Body 永不搬家」一致：header 相当于壳子，data 缓冲区相当于内容。
  代价是多一次间接寻址和分配，可接受。
- `list` 和 `dict` 都采用分离布局；`str` 不变（不可变，单指针）。
- 这是 **ABI 变更，与「移除 `rc` 字段」合并为一次 ABI v2**，不拆成两次改 ABI。
- 配套保守规则：`for` 遍历某变量期间禁止对该变量做 `listAppend`/`listRemove`/`dictRemove`，
  因为 P13-1 还没有子引用冲突检查（属 P13-4）。`for v in xs { listAppend(xs, v) }` 会在遍历中 `realloc`。

### D13 异常边与状态分析

**问题是**：D1 选 A（异常路径不保证销毁）不能只考虑「泄漏」。如果外层所有者在 `try` 体内
被消耗或释放，然后抛出，`catch` 之后作用域末会**再释放一次** —— 这就是双重释放。

**裁决：确认**以下规则：

1. `catch` / `finally` 入口的状态取 `try` 体内**所有可能抛出点**状态的合并。
2. **P13-1 简化为**：`try` 体内禁止移动外层拥有者（含存入容器、整体 `ret` 外层变量），
   违反时报错。这样入口状态恒为 H，不需要条件销毁，也就不会在 `catch` 后双重释放。
3. 顺序：`try` 块局部变量在块出口销毁 → 跑 `finally` → 外层作用域销毁。
   `ret` 穿过 `finally` 时先把返回值移入 `result`，再按这个顺序走。
4. 被抛出的异常对象本身在 P13-1 **不释放**，文档标注为已知泄漏，归属等 P13-2 之后再定。
5. 实现前确认：`longjmp` 回来后局部变量在**栈槽**而非寄存器。**已实测确认成立** ——
   `rcc_codegen.cpp` 的局部变量统一走 `allocateSlot()` 的 `%rbp` 相对槽位，
   `core_eh_throw`（`lib/core/core_win64.s`）从帧块恢复 `%rbp`/`%rsp`，所以 catch 落地后
   本帧槽位仍然有效，不需要改 codegen 的变量布置。

### D14 范围外类型

直接释放必然双重释放）；`list[Foo]` **只释放缓冲区，不释放元素**。留到 P13-2 的 Body 概念定稿后再处理。

#### P13-3 的具体缺口：能力类型的降级链没接通

规范 §3.2 规定三种能力类型只能**降级**（`Take → Mut → Ref`），§3.3 规定
`Take` 实参语法是 `f(take x)`。实测：

| 写法 | 结果 |
|---|---|
| `fun show(p: Ref[Player]): str { ret p.name }` + `show(&p)` | ✅ 输出 `bob` |
| `fun heal(p: Mut[Player])` + `heal(&p)` | ❌ `cannot assign Ref[Player] to Mut[Player]: different memory roles` |
| `fun eat(p: Take[Player])` + `eat(take p)` | ❌ `Compilation failed: syntax errors`（`take` 不是语法） |
| `fun eat(p: Take[Player])` + `eat(p.take())` | ❌ `cannot assign Content[Player] to Take[Player]` |

也就是说：**三种能力类型目前互不兼容**，规范里的降级链一行都没实现。
唯一可用的 `Take` 入口是 Content 的 `x.take()`（取内容，不是能力类型实参），
而 `Mut` 目前只能从容器的 `get_mut()` 拿到，无法从 `&x` 转换。

#### P13-6 / P13-7 的证据

- 成员集合追踪：检索 `cardinality` / `membership` / `重数`，**零命中**。
- `Link`：`code/src/rcc_base.cpp` 与 `rcc_core.cpp` 里有 `TOKEN_LINK`，
  但 `var l: Link[int][int][one] = null` 报 `Unknown type 'Link'`。
