## 3. 待裁决问题（Q1–Q11，全部待审批提案）

### Q1 线程载体（最大前置，代码库零基础）
- 选项方向：OS 线程 / 线程池 / 协程 / 其它。
- 影响：决定运行时 ABI、core 原语、跨界调用约定、join 实现与可移植性。
- **未裁决 → P14-1 不得开工。**

### Q2 `scope` 形态
- 语句 vs 表达式；能否嵌套；join 时机（末尾隐式 join 的精确语义）；作用域内提前返回/异常时的行为（与 Q9 关联）。

### Q3 `spawn` 形态
- `s.spawn(f(args))` 还是关键字形式；遵循 `Take` 二等规则；任务体不隐式捕获外层变量，所有输入通过实参显式传入。

### Q4 并行组合检查
- 效果集从函数签名 `from/writes/ensures` 推导，还是新增专用并发标注；
- "判断不了退回类型级并拒绝"的严格度；
- 与既有实例级路径 / 不等事实 / 成员集合机制的复用方式；
- §12 未决 3（效果集大时的检查复杂度）是否需要原型实测。

### Q5 数据并行原语集
- 规范 §10.4 只定义 `par_each`，但 §10.8 示例出现 `par_zip` / `par_zip_into`：
  纳入首版，还是改写示例只用 `par_each`？
- 闭包体验证规则：只访问 `p` 及子路径、只读捕获的 `Ref` 不能是同类型 T 的其他槽位、不使用 `take`、不调用 Link 原语、不改 pool 结构。

### Q6 `Locked<T>` / `lock`
- 语法形态（`lock c as g { }`）；`g` 为二等值，不能存储/返回，子引用不能逃出块；
- `Locked<T>` 的 `Ref` 可被多任务同时持有，并行检查视其为只读。

### Q7 `Atomic<T>`
- 仅需 `Ref` 即可原子操作、并行检查视只读、永不 `take`；
- 初版只顺序一致；首版提供哪些元素类型。

### Q8 `Chan<T>`
- 规范称"是 `Locked` 的一种"但语义是 Content 所有权转移——两者如何统一；
- `send` 消耗（→ X）、`recv` 在接收方出生地创建 Content、返回 `T?`（关闭为 null）；
- 无取消机制下的阻塞语义（关联 §12 未决 4）。

### Q9 scope 非正常退出
- 异常 / abort / 提前返回时，未 join 任务如何处理（与 §9 中止语义、D1 裁决的关系）。

### Q10 §12 相关未决处置
- 建议排除首版：detached 任务（§12.1）、显式内存序（§12.2）、阻塞取消（§12.4）、异步/协程（§12.5）；
- 需要测量/后续：事实表上限 256（§12.6）；
- 以上均为**建议**，须逐条裁决确认。

### Q11 阶段依赖与挂账项排序
- 挂账项：变长参数（`p12_varargs_proposal.md` Q1–Q8 已裁决未实施）、G1b argv + `prog.entry` 重设计、P13-6/P13-7 审计 §5 后续项、E 项异常对象归属、§12 未决 7–10、自举 S0–S4。
- 需裁决：先清理挂账项，还是与 P14 并行、或明确推后。

## 4. 验收标准

1. 规范 §10.8 粒子系统两阶段示例能用 Rio 语法跑通（阶段 1 并行读、阶段 2 并行写、阶段间由 scope join 分隔）。
2. §10.9 六条竞争排除论证逐条对应到实现：
   - 任务只通过实参获得数据，实参能力决定效果；
   - 任意两方效果不冲突 → 同一内存位置不会一方写另一方读/写；
   - 状态位（F/E、Link 非空）视为内容访问，`take` 与读也不并行；
   - 引用来源出生地包住 scope → 任务运行期间槽位不被销毁；
   - 共享可变状态只经 `Locked`，访问只在 `lock` 块内，二等值不逃逸。
3. 回归套件覆盖：scope/join 基本语义、并行冲突的编译期拒绝、`Locked`/`Atomic`/`Chan` 各一条正向用例、粒子系统端到端用例。
