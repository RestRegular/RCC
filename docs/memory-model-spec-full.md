## 1. 设计目标与非目标

### 目标

1. **每个对象的销毁点在编译期完全确定**，由程序员给出的信息（出生地、签名标注）加编译器推断得出。
2. **没有隐式的运行时检查，没有隐式终止。** 所有动态行为（检查壳子是否为空、加锁、接收消息）都必须在源码里显式出现。
3. 引用是一等公民，可存进变量、结构体、容器。
4. 能直接表达环形、互指、反向边等图结构，不需要 Rc / Weak / 索引。
5. 标注默认由编译器推断；标注只用来"放宽"，缺省保守，且会被编译器验证。

### 非目标

- 垃圾回收、引用计数、运行时版本号。
- 异常展开（见第 9 节：有异常，但不展开、不运行销毁）。
- 防止死锁与活锁（它们是活性问题，不是内存安全问题）。

## 2. 对象模型

### 2.1 两种所有者

| | Body（壳子） | Content（内容） |
|---|---|---|
| 是什么 | 固定位置的槽位 | 一个对象的实际数据 |
| 出生地 | 创建时指定 | 创建时指定；`take` 出来时也要指定 |
| 销毁点 | 出生地结束处 | 出生地结束处 |
| 能否被引用 | 能 | **不能** |
| 状态 | Full / Empty | 持有（H）/ 已消耗（X） |

内容较小时直接内联在壳子里；含堆数据时，壳子里存指向堆的指针。

### 2.2 出生地

创建时必须显式写 `in`：

```
let a = Body.new(Player("Ann", 50, [])) in local     // 当前栈帧，作用域末尾销毁
let b = pool.add(Player("Bob", 30, []))              // 出生在 pool，pool 结束时销毁
return Content.new(...) in result                    // 出生在调用者预留的位置
```

- `local`：接收该值的**绑定所在的作用域**（不是书写位置所在的块，见 8.4）。循环体内即每轮一个。
- 容器（如 `Pool`）：销毁点为容器出生地结束处，或显式 `release`。
- `result`：调用者预留位置。
- 对象存活范围超出当前作用域时，必须**显式**指定外层出生地，编译器不自动提升。

**临时值**（2026-11-17 裁决，D10）：临时值不是新概念，它是**出生地为当前语句的匿名 `local`**，
销毁点是语句末尾。对于 `in ...` 标注，Content 的出生地可由位置推出时可省略，**Body 永远显式**。

**Rio 落地的分阶段口径**（2026-11-17 裁决，D3）：

| 阶段 | Body 出生地 | 临时值出生地 | 语法 |
|---|---|---|---|
| P13-1 | 隐式，恒为 `local` | 隐式，语句级匿名 `local` | **零新增语法**，全靠推断 |
| P13-2 起 | **永远显式**写 `in local` / `in pool` / `in result` | 位置可推出时省略 | 按 P13 计划 §5.2 单独提案 |

也就是说：本节上面的 `in` 写法是**模型的目标形态**，不是 P13-1 的语法要求。
P13-1 里局部变量与临时值都不写 `in`，`ret xs` 的移动由所有权规则自动确定（见 P13 计划 §4 D9）。

### 2.3 永不搬家

- Body 出生后地址永不改变。
- Content 也不搬家：转移 = **消耗旧 Content，在新出生地创建新 Content**（内联部分拷贝，堆数据所有权转交）。旧 Content 变为 X。

### 2.4 销毁

- 销毁只发生在出生地结束处，或显式的 `release` / `clear` 调用处。
- 作用域末尾：若所有者仍为 Full / H，则销毁内容，再回收壳子。
- 每个出口（`break`、`continue`、`return`）按**当前状态**插入销毁，每条正常控制流路径上每个所有者恰好销毁一次。
- 状态在合流处不一致（`?`）时允许**条件销毁**：flag 位于出生地旁，是文档化的机制，不是隐藏行为（布局见 6.5）。
- 销毁逻辑里**禁止**通过引用访问其他本体的内容，因此销毁顺序不影响安全。
- **顺序**（2026-11-17 裁决）：同一作用域内按**声明的逆序**销毁。顺序不影响安全性，
  但逆序更符合直觉、便于排查泄漏。
- **形态**（2026-11-17 裁决 D16）：按**元素类型**生成 drop glue 函数（mangling 名，
  在单态化的实例缓存里去重），各出口只发一次调用，不把整段销毁逻辑内联到每个出口。
  `list[list[str]]` 只对应一个 drop 函数。

## 3. 引用与能力

### 3.1 引用只指向 Body

引用的含义是"这个槽位"，不是"槽位里的那份内容"。因此：

- 引用可以跨 Full → Empty → Full 存活。
- **空壳期间可以新建壳子引用，但不能通过它访问内容。**
- 引用不能比出生地活得久（编译期检查）。

### 3.2 三种能力

| 能力 | 权限 | 数量限制 |
|---|---|---|
| `Ref<T>` | 查看壳子；状态为 Full 时读内容 | 任意多个 |
| `Mut<T>` | 修改内容字段（含 Ref 的全部权限） | 受局部排他约束（第 4 节） |
| `Take<T>` | `take` / `fill` / `clear` / `move_into`（含 Mut 的全部权限） | 独占，同时最多一个；**不要求其他壳子引用消失** |

只能降级（Take → Mut → Ref），不能升级。

### 3.3 `Take` 是二等值

- 只能在**实参位置**创建，语法 `f(take x)`；不能绑定到变量，不能存进结构体或容器，不能返回，不能被逃逸的闭包捕获。
- 因此不需要"线性"（必须恰好用一次），只需要"不逃逸 + 调用内独占"。
- 调用规则见 8.5。

### 3.4 访问规则

| 编译器掌握的状态 | 写法 | 结果 |
|---|---|---|
| 确定 Full | `r.name` | 直接访问，零开销 |
| 确定 Empty | `r.name` | 编译错误 |
| 不确定（`?`） | `r.name` | 编译错误，提示改用 `get()` |
| 不确定 | `r.get()?.name` | 返回 `Maybe`，由程序员处理空 |

- `Ref` 参数默认要求 Full。`Ref<T?>` 表示接受空壳。
- `if let Some(p) = r.get() { ... }` 块内，`p` 为确定 Full 的引用。
- flag 仅被 `get()` 与状态转换读写。

### 3.5 内容转移操作

```
let c = bob.take() in local          // bob: E，c: H；必须写 in
c.hp += 5                            // 可直接在 Content 上操作
bob.fill(c)                          // 等价于 pool.move_into(bob, c)；c: X，bob: F
```

- `take()` 必须指定 `in`，不存在无出生地的内容。
- `move_into` / `fill` 的目标必须是**确定 Empty**；目标为 F 时须先显式 `clear()`（销毁点在 `clear` 调用处）；目标为 `?` 时须先窄化或归一。
- 函数接收 `Content` 参数 = 消耗它。要保留内容，必须落进某个壳子或 `in result`。
- Content 不能被引用；需要被引用时，先 `move_into` 一个壳子。
- `pool.add(x)` 的 `x` 可以是值，也可以是 Content（消耗）。

## 4. 子引用与局部排他

**子引用**指向内容内部（字段、容器元素），按**路径**登记，如 `p.name`、`p.team.captain`。

### 4.1 冲突判据

修改路径 P 与活跃子引用路径 Q 冲突，当且仅当 **P 是 Q 的前缀（含相等）**。

| 修改类型 | 例子 | 单线程下是否可能使子引用失效 |
|---|---|---|
| 原地改值 | `p.hp += 10` | 否 |
| 替换 / 重分配 | `p.name = "Bob"`、`p.items.push(x)` | 是 |

```
let n  = p.name_ref()
p.hp += 10          // ✓ 原地改值
p.score = 99        // ✓ 路径不相交
p.name = "Bob"      // ✗ n 仍活跃
print(n)
```

（并发下原地改值也算写，见 10.3。）

### 4.2 推论

- `take` 等价于对根路径的替换，与**任何**活跃子引用冲突。壳子引用不是子引用，不受影响。
- 容器的动态下标无法区分元素，保守视为冲突；需要时用库的 `split` 接口拆成互不相交的两段。
- 结构体字段里存的子引用**不带路径**，统一按"整个内容"登记（有意取舍，待后续放宽）。

### 4.3 类型级效果

函数的写效果默认记为 `(类型.字段)`，含义是"可能写该类型任意实例的这个字段"，由编译器从函数体推断，接口方法必须声明。

迭代某容器期间，若调用的函数效果含该容器所在的 `(类型.字段)`，且无法证明它碰的不是被迭代的实例，则拒绝。这堵住了"通过存储的引用修改正在被迭代的容器"这个漏洞：

```
fn notify(b: Ref<Button>) {
    for l in b.listeners { l.on_event() }   // on_event 若可能写 (Button.listeners) → 拒绝
}
```

修法：先 `snapshot()` 再迭代。

## 5. 签名标注

三种标注，**均为放宽标注：缺省保守，写了则由编译器检查函数体不超出声明**。

| 标注 | 含义 | 缺省假设 |
|---|---|---|
| `from p.path` | 返回的引用指向 p 的某路径 | 指向 p 的整个内容；多个引用参数时为全部 |
| `writes p.path` | 函数可能替换 p 的某路径（只写传入实例） | 记类型级效果 `(类型.字段)` |
| `ensures p is Full/Empty` | 调用后壳子状态 | 不确定 |

```
fn name_of(p: Ref<Player>) -> Ref<String>  from p.name
fn rename(p: Mut<Player>, s: String)       writes p.name
fn retire(p: Take<Player>)                 ensures p is Empty

retire(take bob)                           // 调用后 bob: E
```

- 返回的引用，来源必须是调用者可见的 Body，不能指向本函数的 local。
- 接口方法 / 动态分发 / 外部接口：函数体不可见，必须手写全部标注。
- 容器的 `adds` / `removes` 效果由编译器从函数体推断，用户代码不写（见 6.3）。
- 用户代码里，绝大多数函数不需要写任何标注。

## 6. 容器与 Pool

### 6.1 稳定地址

Pool 的壳子地址必须永不改变，不允许整体搬迁的连续数组：

| 实现 | 特点 |
|---|---|
| `Pool.chunked(block: N)`（默认） | 分块追加，旧块不动 |
| `Pool.fixed(capacity: N)` | 一整块，最快；满了 `add` 返回 `Maybe` |
| `Pool.boxed()` | 逐个单独分配，最简单 |

### 6.2 槽位回收

- `pool.release(x)`：回收壳子，槽位可被复用。要求**没有任何活跃引用**（壳子引用、子引用都不行）。
- **不引入版本号机制**（避免重新引入运行时失效检查）。
- 不想 release 时，可用 `take` + `fill` 原槽位复用（引用的含义本来就是"这个槽位"），或 `pool.add_reusing(...)` 优先填空槽。

操作约束一览：

| 操作 | 活跃壳子引用 | 活跃子引用 |
|---|---|---|
| `p.name` 读写 | 需确定 Full | 无关 |
| `take` / `fill` | 可以 | 不可以 |
| `release` | **不可以** | 不可以 |
| pool 销毁 | 不能晚于 pool | 不能晚于 pool |

### 6.3 成员追踪

对存引用的容器，编译器记录成员集合，用于证明 `release` 安全。

**数据结构**：集合按**路径**索引（局部变量 `team`、字段路径 `game.team`），值为映射：

```
slot 或 *@L  →  重数 ∈ {1, many}    （不在映射中 = 0）
```

加整体兜底 `⊤`（完全未知）。`*@L` 表示第 L 行动态新建的未知槽位。重数饱和：`1 + 1 = many`，格高度有限。

**原语效果**

| 操作 | 集合变化 |
|---|---|
| `push(x)` / `insert(x)` | x 重数 +1（饱和） |
| `remove_one(x)` | 重数 1 → 0；`many` → `many`（保守） |
| `remove_all(x)` | x → 0（精确） |
| `clear()` | 全部清空 |
| `pop_known()` | 返回 `(slot, 新集合)`，集合精确减去该 slot |
| `snapshot()` | 新容器集合 = 原集合的拷贝 |
| `extend(other)` | 并入 other 的集合（重数相加） |
| `retain(f)` / `remove_if(f)` | 集合不变（保守上界） |
| 循环中动态加入 | 加入 `*@L`，重数 many |

**嵌套与传递闭包**

- 容器的容器：有效成员集合是内层所有集合的并（展平），重数相加。
- 结构体：字段按路径分别追踪；对局部变量或 Body 内容里的路径，字段敏感地追踪。
- 经引用访问的结构体：通过 `Ref<Game>` 到达的 `game.team`，集合取 `⊤`，除非效果声明另有说明。
- 拷贝容器等价于 `snapshot()`。
- 闭包捕获含引用的容器时，闭包的集合并入被捕获的集合。

**活跃性**：只有**活跃**容器参与 `release` 判据，即此后还可能被读取、被迭代、被作为实参传出。死变量的集合不计入。

**函数边界**

- 效果由编译器从函数体推断，用参数路径表达：`adds r → c`、`removes r from c`、`clears c`。
- 基础原语 `store` / `take_out` / `drop_all` 由编译器内建识别，上层容器自动组合。
- 返回值若含引用，其集合以参数集合表示：`result ⊆ set(p) ∪ {new@L}`。
- 无法推断（外部接口、动态分发）则必须手写，缺省 `⊤`。

### 6.4 `release(x)` 的判据

> 所有活跃的集合路径中，x 的重数为 0；没有活跃的 x 的壳子引用变量与子引用；壳子状态已 E；若 x 含 Link，则 Link 状态为"空"且 x 不在任何 Link 中（见 7.4）。

### 6.5 状态位与 flag 的布局

- **局部所有者**：只有出现条件销毁的所有者才生成 flag；flag 打包进该栈帧的位图，1 位 / 所有者；循环体内每轮开头复位。
- **Pool 槽位**：每个 chunk 带一个侧位图，每槽位 2 位：`full`、`links_nonempty`。所有 Pool 一律带，不做按类型推断。
- `get()`、`is_full()`、条件销毁、`take` / `fill` 读写的都是这些位。

## 7. Link：成对引用

对称关系（反向边、父子、双向链表）由语言提供的唯一一个特殊原语 `Link` 表达。

### 7.1 声明

```
struct User {
    name:    String,
    follows: Link<User, fans,    many>,
    fans:    Link<User, follows, many>,
}

struct Node {
    val:      i32,
    parent:   Link<Node, children, opt>,
    children: Link<Node, parent,   many>,
}
```

基数：`opt`（至多一个）、`one`（恰好一个）、`many`（任意多个）。编译器检查对偶声明互相指向、字段类型一致。

### 7.2 原语（所有变更必须成对）

| 操作 | 效果 |
|---|---|
| `a.L.add(b)` | 同时执行对偶端的 `add`；a、b 须确定 Full，且尚未相连 |
| `a.L.remove(b)` | 同时从对偶端移除 |
| `a.L.clear()` | 对每个邻居移除对偶边 |
| `a.unlink_all()` | 清空 a 的所有 Link 字段，两端同步 |
| `n.parent.set(p)` | 按基数自动从旧对端移除，再加入新对端 |

用户代码拿不到单边修改接口，"一半有一半没有"的状态不可构造。自环合法（两个字段路径不相交）。

### 7.3 不变量

> 任一时刻，`x ∈ a.L` 当且仅当 `a ∈ x.L'`；且 Link 里的每个引用指向的壳子都是 Full。

由 Link 实现内部（唯一允许写单边的受限 `trust` 块）维护，编译器据此信任。

### 7.4 对其他规则的影响

- **遍历**：Link 内元素保证 Full，`for f in u.fans { print(f.name) }` 无需 `get()`。
- **take**：要求所有 Link 字段此刻确定为空，否则须先 `unlink_all()`。
- **release**：要求 Link 状态为空，且 x 不在任何 Link 中。
- **状态格**：含 Link 的本体多追踪一个事实"Link 是否确定为空"，与 F / E 同一套机制。

### 7.5 与类型级效果的交互

`a.follows.add(b)` 的效果有两个粒度：

- **类型级**：`(User.follows)` 与 `(User.fans)`。
- **实例级**：`a.follows` 与 `b.fans`。

编译器**先用实例级**判断。迭代 `u.fans` 期间，Link 原语的调用与迭代冲突，当且仅当其某个对端可能就是 `u`。若无法证明不是，退回类型级并拒绝。

**不等事实（`a ≠ b`）的来源**

1. 同一 pool 的两次 `add` 返回的 slot 互不相同（中间未 release 时）。
2. 新建的 Body 与任何已存在的 slot 不同。
3. `if a.is(b) { .. } else { <此处 a ≠ b> }`。
4. Link 基数：`one` / `opt` 的对端若已知非空，则与别的对端不同；`many` 不提供。
5. 迭代 `snapshot` 时，循环变量与被迭代集合以外的 slot 的关系，一般**不能**推出 `f ≠ u`，除非先 `is` 判断排除自身。

**Link 事实的失效**：事实 `bob.links = 空` 在下列情形保持，否则回到 `?`：

- 其间没有以 bob 为端点的 Link 原语调用；
- 其间没有**可能给 bob 加边**的调用（调用的类型级效果含该 Link 字段的 add，且调用方能触及 bob）。
- 保守规则：`unlink_all` 与 `take` / `release` 之间**不允许**夹杂带 Link-add 类型级效果的调用。

**迭代 Link 的典型模式**

```
// 只读遍历：无限制
for f in u.fans { print(f.name) }

// 遍历中改邻居
for f in u.fans.snapshot() {
    if f.is(u) { continue }          // 得到 f ≠ u
    f.follows.remove(u)
}
// 推荐写法：直接 u.unlink_all()
```

### 7.6 边界

- Link 只保证内存安全与对偶一致，**不保证无环**；无环由 `Tree` 等库在 `set` 里自行检查。
- 两端必须在**同一个 Pool**，禁止跨池 Link。
- 单向引用（缓存、observer）用普通 `List<Ref<T>>` + 成员追踪；需要严格释放时升级为 Link。
- 只覆盖成对关系；三方关系拆成多个 Link。

### 7.7 标准删除写法

```
bob.unlink_all()
let gone = bob.take() in local
log("removed " + gone.name)
pool.release(bob)
```

## 8. 控制流与状态窄化

### 8.1 程序点上维护的事实

编译器对每个程序点维护事实表，按 **slot（槽位身份）** 索引：

| 事实 | 取值 |
|---|---|
| 壳子状态 | F / E / `?` |
| Content 状态（按变量） | H / X / `?` |
| Link 是否为空 | 空 / 非空 / `?` |
| 不等事实 | `a ≠ b` |
| 窄化事实 | 见 8.2 |

合流时逐项取格上界。事实格每一维高度有限，循环取不动点必然终止：

```
循环头状态 S = 进入前状态
重复：
    沿循环体推演，得到回边状态 B
    S' = 合并(S, B)
    若 S' == S：停止
    否则 S = S'
```

事实表是稀疏的：只为函数内被触及的 slot 建条目；别名类用并查集合并（仅限函数内）。超过上限（默认 256 个被触及 slot）时，超出部分降级为 `?` 并给出诊断；这是保守降级，不影响安全。

### 8.2 窄化的来源

| 写法 | 窄化结果 |
|---|---|
| `if let Some(p) = r.get() { A } else { B }` | A 中 r: F，`p` 为确定 Full；B 中 r: E |
| `match r.get() { Some(p) => .., None => .. }` | 同上 |
| `let Some(p) = r.get() else { return }` | else 分支发散，其后 r: F |
| `if r.is_full() { A }` | A 中 r: F；`is_empty()` 同理 |
| `a && b` / `a \|\| b` | 按短路求值逐子条件窄化 |
| `if a.is(b) { .. } else { .. }` | else 分支得到 `a ≠ b` |

窄化后的合流：`if let` 之后（无发散）r 为 `?`，除非两支都把它推到同一状态。

### 8.3 窄化的作用对象与失效

窄化的对象是 **slot**，不是变量。

- **身份已知**：来自 `pool.add(..)` 的结果、`let r2 = r` 的拷贝。窄化对所有这些别名同时生效。
- **身份未知**：来自容器元素、函数返回值。窄化只记在该变量及其拷贝上。

**失效规则**：窄化事实回到 `?`，当且仅当：

1. 执行了带 `take x` 实参的调用，且被窄化的引用与 x 类型相同、又不能证明 `r ≠ x`；
2. 调用的 `ensures` / 效果声明了对该类型壳子状态的修改；
3. 循环回边（窄化不跨回边保持，须每轮重新建立）。

纯 `Ref` / `Mut` 调用不会使窄化失效，因为它们没有改变壳子状态的能力。

**闭包**：不带走窄化事实，闭包内捕获的 `Ref` 按 `?` 处理。只在创建点同步调用的二等闭包等价于内联，沿用调用点的事实。

### 8.4 `if` / `match` / 块作为表达式：目的地传递

值产生表达式接收一个**目的地**，即接收它的绑定的出生地：

```
let c: Content<Player> in local = if cond { Content.new(Player("Ann")) }
                                   else    { Content.new(Player("Bob")) }
```

1. `in` 写在绑定上；目的地传递到各分支的**尾表达式**，尾表达式直接在目的地构造，不产生中间值，也不会在块结束时被销毁。
2. 块内部的其他绑定是块自己的 local，块结束时销毁。
3. 尾表达式是已有所有者时（`if cond { a } else { b }`）：被选中的所有者被消耗，目的地新建内容；未选中的保持 H。合流后 `a`、`b` 都是 `?`，产生条件销毁。这是**警告**；模块级 `#[strict_destroy]` 把它升级为错误。
4. `return <表达式> in result` 同理，目的地为 `result`。
5. 目的地为 Body 时，仅允许 `result`，且尾表达式必须是新建。

### 8.5 `Take` 实参的调用规则

设调用 `f(take x, args...)`：

1. **不重叠**：其余实参中不得有可能指向 x 同一 slot 的 `Ref` / `Mut` / `Take`，除非能证明 `≠`。理由：被调函数若通过 `Ref` 读内容，而 `Take` 已取走内容，会读到空壳。
2. **不逃逸**：被调函数内 `Take` 形参只能用于内建转移操作、降级为 `Mut` / `Ref` 临时传出、或再次作为 `take` 实参传下去。降级期间原 `Take` 暂停。
3. **后置状态**：以被调函数的 `ensures` 为准，缺省 `?`；函数体会被验证。
4. **经由容器的间接访问**：容器元素的状态为 `?`，读内容必须 `get()`，因此安全；Link 元素保证 Full，所以对含 Link 的对象，`take` 要求 Link 先空。

### 8.6 返回

| 返回 | 规则 |
|---|---|
| `Ref<T>` | 来源必须是调用者可见的 Body，`from` 指向参数或其路径 |
| `Content<T>` | 必须 `in result`：直接新建，或消耗本函数内某个 Content 后在 result 新建 |
| `Body<T>` | 只能在 result **直接出生**，不能"返回已有 Body" |

条件返回不同 Content 合法：每个分支消耗自己的 local，在 result 新建；各出口按当时状态销毁其余所有者。

条件产出 Body 时，使用调用者提供的壳子（out 参数）：

```
fn pick_into(cond: bool, slot: Take<Player>) ensures slot is Full {
    let c: Content<Player> in local = if cond { Content.new(..) } else { Content.new(..) }
    slot.fill(c)
}
```

### 8.7 出口与销毁

`break` / `continue` / `return` 出口按当前状态插入销毁；循环后状态为所有出口状态的合并；窄化事实随出口一起合并。

**异常出口**（2026-11-17 裁决 D13）：`throw` 不是销毁出口 —— 它不运行沿途销毁（见第 9 节）。
但 `catch` / `finally` 的入口状态必须取 `try` 体内所有可能抛出点状态的**合并**，
否则落地后重新进入正常控制流时会重复销毁。P13-1 的简化做法是**禁止在 `try` 体内移动外层拥有者**，
使该合并退化为「与进入时相同」。

### 8.8 循环中的出生地与子引用

- 循环体内 `in local` 的所有者每轮新建、每轮销毁。
- 循环里需要活过循环的对象，必须显式指定外层出生地。
- 子引用登记同样做不动点；若某轮创建的子引用活到下一轮，下一轮的 `take` / 替换会与之冲突并被拒绝。

## 9. 失败与中止

> **2026-11-17 用户裁决（D1 = A + D13）**：本节原稿写「没有异常」，但 Rio 早在 P7 就已实现并
> 验收了 `try` / `catch` / `finally` / `throw`（显式帧链，setjmp/longjmp 风格，
> `core_panic_raise` 在 `lib/core/core_win64.s`）。因此**保留异常**，并按下面的取舍改写不变量。

### 9.1 基本取舍

- **有异常，但没有展开（unwinding）。** 异常沿着显式帧链长跳，**不运行任何沿途销毁**。
- 可恢复失败仍推荐用 `Result` / `Maybe` 显式表达；异常是已有的语言特性，不强制使用。
- 不可恢复的情况（`abort()`、内存耗尽）直接终止进程，**不运行任何销毁**。
- 因此「每个对象恰好销毁一次」这条不变量**只在正常控制流路径上成立**；
  异常路径**不保证**销毁，等价于「异常即泄漏」。这是显式接受的代价。

### 9.2 与 D13 的配套规则（防止泄漏变成双重释放）

只说「异常即泄漏」是不够的：若某个外层所有者在 `try` 体内被消耗或释放，然后抛出，
`catch` 之后作用域末尾会**再释放一次**——这就是双重释放。所以必须配套：

1. **入口状态取合并。** `catch` / `finally` 入口的状态，取 `try` 体内**所有可能抛出点**
   状态的合并（格上界）。只有这样才能保证之后的销毁决策对每一条落地路径都成立。
2. **P13-1 的简化规则。** 在 P13-1（只有 H/X 两档、Body 恒 Full）里，
   **禁止在 `try` 体内移动外层拥有者**（含存入容器、整体 `ret` 外层变量），违反时**编译报错**。
   这样 `catch` 入口状态恒为 H，不需要条件销毁，也就不会在 `catch` 后双重释放。
   等 P13-2 有了 F/E/`?` 与条件销毁（flag 位图，§6.5）后再放宽为完整的状态合并。
3. **销毁与 `finally` 的先后顺序。** `try` 块的局部变量在块出口销毁 → 再跑 `finally`
   → 最后才是外层作用域销毁。`ret` 穿过 `finally` 时，先把返回值移入 `result`，再按这个顺序走。
4. **异常对象本身的归属。** P13-1 **不释放**抛出的异常对象，明确标注为**已知泄漏**；
   归属（出生在哪、谁销毁）等 P13-2 之后再定。
5. **栈槽可信性。** 长跳回来后局部变量所在**栈槽**必须仍然有效。已实测确认成立：
   Rio 的局部变量统一走 `%rbp` 相对槽位（`rcc_codegen.cpp` 的 `allocateSlot`），
   `core_eh_throw` 从帧块恢复 `%rbp`/`%rsp` 后才跳到 resume 地址，
   因此不存在「值在寄存器里被冲掉」的问题。

### 9.3 代价

中止与异常时，文件、锁等资源不会被清理，依赖操作系统回收。对应地，本模型**不承诺**
异常安全（exception safety）级别的资源清理。

## 10. 并发（首版：结构化并发）

### 10.1 总原则

1. 线程**不能比出生地活得久**；并发里把线程当成"持有引用的东西"，沿用既有检查。
2. 首版只支持**作用域内的任务**，作用域结束即 join，销毁点仍然静态确定。
3. 数据竞争的排除靠**效果的并行组合检查**，不靠运行时。
4. 一切动态行为（加锁、阻塞、接收）必须在源码里显式出现。

### 10.2 作用域与任务

```
scope s {
    s.spawn(work(take a, cfg))       // cfg: Ref<Config>
    s.spawn(work(take b, cfg))
    log(cfg.name)                    // 父线程的后续代码也是并行的一方
}                                    // 作用域末尾：隐式 join
```

- `spawn` 的实参遵循普通调用规则，包括 `Take` 的二等规则。
- 任务体不能隐式捕获外层变量，**所有输入通过实参显式传入**。
- 任务实参里所有引用的来源，其出生地必须**包住整个 scope**。
- join 之后，父线程对任务触及的 slot 的事实全部回到 `?`。

### 10.3 并行组合检查

设 scope 内有任务 `T1..Tn` 以及父线程从 `spawn` 到 scope 末尾的后续代码 `P`。每一方有效果集：

| 记号 | 含义 |
|---|---|
| `R` | 读的路径（读内容同时读状态） |
| `W` | 写的路径（替换 / 重分配 / **原地改值**都计入） |
| `S` | 改变壳子状态的 slot |
| `L` | Link 原语，视为对两端字段的写 |

对每一对 `(X, Y)` 要求：

- `W_X` 与 `R_Y ∪ W_Y` 不可能重叠；
- `S_X` 与 `R_Y ∪ W_Y ∪ S_Y` 不可能重叠；
- `L_X` 按其两端字段并入 `W_X`；
- 读读不冲突。

"不可能重叠"用既有机制判断：实例级路径 + 不等事实；判断不了则退回类型级并拒绝。并发下原地改值也冲突，因为两个线程同时写同一整数就是数据竞争。

### 10.4 数据并行原语

```
pool.par_each(|p: Mut<T>| { ... })
```

编译器验证闭包体：

- 只访问 `p` 及其子路径（写），以及显式捕获的 `Ref`（只读；这些只读数据不能是同类型 T 的其他槽位，除非整个 `par_each` 内无任何写）；
- 不对其他 slot 使用 `take`，不调用 Link 原语，不改 pool 结构。

每个槽位恰好被访问一次，元素互不相交，无需逐对证明。需要读邻居的算法用**两阶段**写法，阶段间由 scope 的 join 分隔。

### 10.5 Pool 的并发结构修改

- `chunked` 的 `add` 不搬动已有槽位，与元素访问物理上不冲突。`add` 的效果记在 **pool 级路径**，只与其他结构修改（`add` / `release` / 遍历 pool）冲突。
- 多任务同时 `add`：使用 `Pool.chunked(concurrent: true)`，内部用原子游标与 CAS 追加 chunk，并声明"并发安全的 `add`"，允许多个任务同时调用。
- `release` 总是独占。
- `fixed` / `boxed` 的并发版本以后再加。

### 10.6 显式锁与原子

```
let counter: Locked<Stats> = Locked.new(Stats(0)) in local
scope s {
    s.spawn(work(counter.share()))                 // Ref<Locked<Stats>>
}
// 任务内：
lock c as g {                                      // 显式加锁，可能阻塞
    g.hits += 1                                    // g: Mut<Stats>，二等值
}
```

- `Locked<T>` 是特殊的 Body：只能通过 `lock ... as g { }` 访问内容。
- `g` 是二等值：不能存储、不能返回，其子引用也不能逃出块。
- `Locked<T>` 的 `Ref` 可被多个任务同时持有，并行检查视其为只读。
- `Atomic<i32>` 等原子类型：只需要 `Ref` 就能做原子操作，并行检查视其为只读，永不 `take`。初版只提供顺序一致。
- 死锁不被防止；可选 lint：同一作用域内锁顺序不一致给警告。

### 10.7 通道与 Content 传递

```
let ch: Chan<Msg> = Chan.new() in local
ch.send(c)                                         // 消耗 Content c（→ X），堆数据所有权转交
let m = ch.recv() in local                         // 阻塞；返回 Maybe<Content>（通道关闭为 None）
```

- `Chan<T>` 是 `Locked` 的一种，`share()` 后双方持 `Ref`。
- `send` 消耗，`recv` 在接收方指定的出生地创建 Content，没有共享，因此没有竞争。
- Content 内含的引用，其来源出生地必须包住整个 scope。

### 10.8 示例：粒子系统

```
fn step(pool: Take<Pool<Particle>>, cfg: Ref<Config>) {
    let forces: Pool<Force> = Pool.fixed(capacity: pool.len()) in local
    scope s1 {                                      // 阶段 1：并行读
        pool.par_zip_into(forces, |p: Ref<Particle>, f: Mut<Force>| {
            f.value = compute_force(p, cfg)
        })
    }
    scope s2 {                                      // 阶段 2：并行写
        pool.par_zip(forces, |p: Mut<Particle>, f: Ref<Force>| {
            p.vel += f.value * cfg.dt
        })
    }
}   // forces 在此销毁
```

### 10.9 排除数据竞争的论证草图

1. 任务只通过实参获得数据，实参的能力决定其效果。
2. 并行组合检查要求任意两方效果不冲突，所以同一内存位置不会被"一方写、另一方读或写"同时访问。
3. 状态位（F / E、Link 非空）被视为内容访问的一部分，所以 `take` 与读也不并行。
4. 引用的来源出生地包住 scope，所以任务运行期间所指槽位不会被销毁。
5. 共享可变状态只通过 `Locked`，访问只在 `lock` 块内，块内二等值不逃逸。
6. 未被静态覆盖的只有死锁与活锁。

## 11. 示例与编译器错误信息

### 11.1 回合制小游戏

```
fn main() {
    let pool: Pool<Player> = Pool.chunked(block: 64) in local
    let team: List<Ref<Player>> = List.new() in local    // 在 pool 之后声明
    let ann = pool.add(Player("Ann", 50, []))
    let bob = pool.add(Player("Bob", 30, []))
    team.push(ann); team.push(bob)

    heal(ann)                                // F → F
    let n = name_of(ann)                     // 登记 ann.name 上的子引用
    print(n)                                 // n 最后一次使用，注销
    rename(ann, "Anna")                      // ✓

    let c = bob.take() in local              // bob: E，c: H（team 里的 bob 壳子引用可存活）
    c.hp += 5
    if c.hp > 20 { bob.fill(c) }             // c: X，bob: F
    else         { archive(c, graveyard) }   // c: X，bob: E；合流 bob: ?
    if let Some(p) = bob.get() { show(p) }

    team.clear()
    pool.release(bob)
}
```

### 11.2 图（含环）

```
let pool: Pool<User> = Pool.chunked(block: 64) in local
let ann = pool.add(User("Ann"))
let bob = pool.add(User("Bob"))
let cat = pool.add(User("Cat"))
ann.follows.add(bob)
bob.follows.add(cat)
cat.follows.add(ann)                         // 环：无需特殊处理，销毁点唯一（pool）
```

### 11.3 三个反向检验的结论

| 程序 | 结论 | 发现 |
|---|---|---|
| 树的父指针 | 能写，比 Rust 简单 | Link 需基数；无环要库检查；删除要弹出式迭代 |
| 观察者 | 能写 | 严格释放需升级为 Link |
| LRU 缓存 | 能写，槽位复用很自然 | 库要负责清理 map |
| 通知循环 | 暴露漏洞 | 已由类型级效果修复（4.3） |

### 11.4 错误信息格式要求

错误信息必须展示**推断链条**，而不只是结论。

子引用冲突：

```
错误：不能清空 x（L4）
  原因：x 的内容内部存在活跃子引用
    n 在 L3 由 x.name_ref() 创建，指向 x.name
    n 在 L5 仍被使用，晚于清空点
提示：把 L5 的使用挪到 L4 之前，或在清空前结束 n，或改为拷贝
```

循环状态不一致：

```
错误：show(ann) 要求 ann 为 Full（L2）
  循环头状态：? = 进入前 F ∪ 回边 E
  回边的 E 来自 L4：archive 消耗了 ann 的内容
```

release 被拒：

```
错误：不能 release(ann)（L27）
  原因：ann 可能仍在活跃容器 team 的成员集合中
    team 的成员集合：{ann: many, *@L12}（L12 的循环动态加入）
提示：用 remove_all 精确移除，或改用 take + fill 复用槽位
```

并行冲突：

```
错误：任务与父线程的效果冲突（L8）
  任务 spawn(work(take a, cfg)) 写 a.score
  父线程 L9 读 a.score
  无法证明二者访问的不是同一槽位
提示：把 L9 挪到 scope 之后，或使用 Locked
```

## 11A. 内置容器 `list` / `dict` 在模型中的定位

> 2026-11-17 用户裁定：**内置 `list` / `dict` 不需要任何新机制**。
> 它们就是「一个 Body + 一块堆内存」，本文档已有的规则直接适用。
> 本节只把这条对应关系写清楚，不引入新概念。

### 11A.1 结构

| 语言层 | 模型层 |
|---|---|
| `var xs: list[int]` 这个变量 | **Body（壳子）**，出生在当前栈帧 |
| 堆上那块 `ListHeader + data[]` | **Content（内容）** |
| `var ys = xs` | 壳子赋值（默认共享同一内容，直到某方被替换） |
| `xs[i]` | 指向内容的**子引用**，路径 `xs[*]` |
| `xs.items` / `xs.items[*]` | 同上，路径按 §4 的规则登记 |

**P13-1 的可实现形态**（2026-11-17 裁决，D15）：局部变量这个 Body 在 P13-1 里是
**隐式的**——没有语法、恒为 Full、没有 F/E 状态，编译器只追踪它的 H/X。
也就是说上表是模型定位，P13-1 只落地其中「销毁点 = 作用域末」这一半。
Body 的显式语法从 P13-2 起引入。

**元素本身不是 Body。** 元素只是内容里的一块字节；`xs[0]` 取出来的是值或子引用，
不会为它新建壳子。这条是本节最要紧的一句 —— 一旦把元素当 Body，
就会凭空多出一层生命周期与销毁点，而那层并不存在。

**别名与销毁**（2026-11-17 裁决，D9）：`var ys = xs` 在 P13-1 被解释为**对 `xs` 壳子的隐式引用**
（借用），不产生第二个拥有者，因此不产生第二个销毁点。只有「新值初始化的变量」才是拥有者。
到 P13-3 引入 `Ref` / `Mut` / `Take` 后，这条隐式规则被能力类型取代。

**布局要求**（2026-11-17 裁决，D12）：壳子（=`ListHeader`）的地址必须永不改变，
因此 header 与 `data[]` **分离分配**，扩容时只 `realloc` data 缓冲区。
单指针紧凑布局（`header + data[]` 连体）与 §2.3「Body 永不搬家」冲突，已否决。

### 11A.2 销毁

`xs` 的销毁点 = 作用域末（`in local`）或返回值转移（`in result`），
由编译器**在编译期**确定，与 §3 的出生地规则完全一致。

销毁动作 = 对**元素类型**生成释放代码，再释放容器本身。元素类型的销毁代码在
编译期由 `list[T]` 的 `T` 展开：`T` 是标量时无需逐元素处理；`T` 是 `str` /
`list` / `dict` 时逐元素递归释放。**不存在运行期按类型标签分派**，
因为 `T` 在单态化时就已知。

### 11A.3 `dict` 的键

键是只读的：`d[k]` 取到的键只能得到 `Ref`，永远不给 `Mut`。
理由是改键会破坏查找结构（键槽与值槽是两个独立的线性数组，见 11A.4）。
值的可写性由值类型决定，与键无关。

### 11A.4 当前实现与模型的差距

P12 的 `lib/std/ds.rio` 按现有后端能力实现，与模型的差距是**已知且已登记**的。
**2026-11-17 裁决（D6/D12）**：前三行的归属从 P13-2 提前到 **P13-1**，并与「移除 `rc`」
合并为一次 **ABI v2**（不拆成两次改 ABI）。

| 现状 | 模型要求 | 归属 |
|---|---|---|
| `listAppend` 返回**新列表**（索引写入有边界检查，无法原地追加） | 原地追加 | **P13-1** |
| `listRemove` / `dictRemove` 原地 shift-left + 改长度头 | 一致 | 已完成 |
| `copy` 是**浅拷贝** | `clone()` 深拷贝 | **P13-1** |
| 从不调用 `core_free` | 销毁点生成释放代码 | **P13-1** |
| `list` / `dict` 是**单指针紧凑布局**（`header + data[]` 连体） | header 与 data 分离（§11A.1） | **P13-1（ABI v2）** |
| `dict` 的 `keys` / `vals` 是两个独立的线性 8 字节槽数组 | 无要求（实现细节） | — |
| 遍历顺序 = 插入顺序 | 无要求 | — |

`rc` 字段恒为 0，已标注废弃（见 `docs/architecture_plan.md §8.1`）；
**P13-1 一并移除该字段**，与上表的布局变更合成 ABI v2。

`core_free` 的三条语义（2026-11-17 裁决，D5 + D11）：

| 输入 | 行为 |
|---|---|
| `nullptr` | 静默返回 |
| `cap == 0` 的 header（`str` 字面量的静态只读头） | 静默返回 |
| 重复释放 | **未定义行为**，不加运行期检查 |

第二条是对**值表示的约定**（`cap==0` 即不可释放），不是隐式运行时检查。
理由：字面量在架构文档 §4.2 里是零分配、指向静态只读区，对它调 `core_free` 会直接崩；
而「每个字面量绑定时复制一次」会让所有字面量变成堆分配，与该设计冲突。

## 12. 未决问题

> **2026-11-17 已裁决项**：原第 1 条「异常 / 中止语义」已定（D1 = A，见第 9 节），
> 不再是【待确认】。下面按当前仍未定的顺序重新编号。

1. **脱离作用域的任务（detached）**：初步构想 `in global` 出生地，生命周期等于进程，共享变更只能经 `Locked` / `Atomic`。尚未设计。
2. **内存序**：初版仅顺序一致，是否开放显式内存序。
3. **并行组合检查的复杂度**：手写 `spawn` 且任务多、效果集大时的成本，需要实测。
4. **阻塞与取消**：`recv` / `lock` 阻塞时 scope 如何协作取消；目前无取消机制。
5. **异步 / 协程**：与出生地、二等值的交互完全未设计。
6. **事实表上限**：默认 256 个被触及 slot 只是占位值，需要原型实测。
7. **结构体字段内的子引用路径**：目前统一按整个内容登记。
8. **跨池 Link**：目前禁止。
9. **三方关系**：需拆成多个 Link，是否需要一般化。
10. **`trust` 块的治理**：范围限定在 Link 等库原语内部，用户代码是否允许及如何审计，未定。
11. **容器元素路径**：动态下标保守冲突，`split` 的类型规则未细化。
12. **推断签名的跨模块兼容**：推断出的签名保存在库的编译产物里，版本兼容策略未定。
13. **条件销毁诊断**：8.4 第 3 点的警告 / 错误边界是否合适。
14. **P13-2 的类型系统前置缺口**（2026-11-17 裁决 D19，登记）：本规范依赖
    `struct`、`Maybe`、`if let` / `match`，而 Rio 目前只有**引用语义**的 `class` 和 `T?`。
    `class` 的 `var b = a` 是**指针拷贝**，与 Content 的唯一所有权直接冲突。
    在 P13-2 开工前必须单独裁决「值语义结构体从哪来」，否则 P13-2 无法落地。
15. **异常对象本身的出生地与归属**：第 9 节 9.2 第 4 条定为「P13-1 不释放」，长期归属待定。

## 附录 A：与 Rust 的主要差异

| | Rust | 本模型 |
|---|---|---|
| 对象位置 | move 时可能改变 | 出生后永不改变 |
| 引用指向 | 当前所在变量 | 稳定的槽位（壳子） |
| 出生地 | 隐式（变量作用域） | 显式（`in ...`） |
| 内容转移 | 整体 move | 消耗旧内容、在新出生地创建 |
| 引用独占 | `&mut` 独占 | `Take` 独占 + 局部排他，壳子引用可跨转移存活 |
| 动态检查 | 隐式（RefCell 等） | 只通过显式 `get()` / `lock` |
| 图 / 互指 | Rc / Weak 或索引 | Pool + Link，直接表达 |
| 展开 | panic 展开 | 无展开，显式 abort |
| 并发 | Send / Sync + 借用 | scope + 效果并行组合检查 |

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| Body（壳子） | 固定位置的槽位，永不搬家 |
| Content（内容） | 对象的实际数据，可转移，不可被引用 |
| 出生地 | 所有者被创建的位置，决定其销毁点 |
| 壳子引用 | 指向 Body 的引用，含义是"这个槽位" |
| 子引用 | 指向内容内部的引用，按路径登记 |
| F / E / `?` | Body 的 Full / Empty / 不确定 |
| H / X | Content 的持有 / 已消耗 |
| 局部排他 | 修改路径 P 与活跃子引用 Q 冲突当且仅当 P 是 Q 的前缀 |
| 二等值 | 只能作为实参 / 块内局部存在，不能存储、返回、逃逸 |
| 成员集合 | 编译器对容器内壳子引用的追踪记录 |
| 不等事实 | `a ≠ b`，用于实例级效果判断 |
| 目的地 | 值产生表达式接收结果的出生地 |

## 附录 C：规则速查

1. 销毁点 = 出生地结束处，编译期确定。
2. Body、Content 都永不搬家；Content 转移 = 消耗 + 新建。
3. 引用只指向 Body，不能比出生地活得久。
4. 空壳期间可建引用，不能访问内容；访问分 Full / Empty / `?` 三档，`?` 必须 `get()`。
5. `Take` 只能在实参位置创建，二等，独占，不要求其他壳子引用消失。
6. `take` 与任何活跃子引用冲突；`release` 与任何活跃引用冲突。
7. 局部排他：P 是 Q 的前缀才冲突；原地改值单线程不冲突，并发下冲突。
8. 标注（`from` / `writes` / `ensures`）只放宽，缺省保守，函数体被验证。
9. `move_into` 目标必须是确定 Empty；销毁旧内容必须显式 `clear()`。
10. Body 只能在 `result` 直接出生；条件产出用调用者提供的壳子。
11. Link 成对修改，Link 内元素恒为 Full；`take` 前须 Link 空；`release` 前须不在任何 Link 中。
12. 成员集合带重数，按路径追踪，只有活跃容器参与 `release` 判据。
13. 无隐式运行时检查；动态行为只来自 `get()`、`lock`、`recv`。
14. 无展开；不可恢复失败直接中止，不运行销毁。
15. 线程只在 scope 内，不能比出生地活得久；并行方效果两两不冲突。
