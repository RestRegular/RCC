## 1. §1 Pool 类型与出生地 —— 语义闭环，语法形态有 1 处冲突

### 1.1 语义裁决状态：✅ 完整，无需用户再裁决

- Pool 是标准库普通类型、三种分配策略、`fixed` 满时 abort（不引入 `T?`）、
  砍掉 `pool.add`、出生地只靠标签区 + `pool.new[T]`、出生地只能指定一次、
  临时 Body 有语句级匿名 local、双角色——全部已明确。
- §1.6 明确"AST 编码是实施细节，判定顺序已定"——无需用户裁决。

### 1.2 与现有语法的冲突（实测）

| 探针 | 当前结果 | 冲突性质 |
|---|---|---|
| `var p: Pool = Pool.fixed(100)` | `Unknown type 'Pool'` | 预期：Pool 类型未实现，非语法冲突 |
| `var a: Player p1 = Player("b")`（标签区出生地） | 解析成两个 label，当前报"无法确定对象类型" | **语法层已能解析**，但需新增"出生地标签"识别与 Pool 变量消歧 |
| `var a: Player = p1.new[Player]("b")` | AST 是 `FunctionCallNode(.)` + right=`IndexExpressionNode(new[Player])` | **明确语法形态冲突**：codegen `emitMethodCall` 期望 right 是 IdentifierNode，这里是 IndexExpressionNode |

**结论**：`pool.new[T](...)` 的"方法名带类型实参"形态需要 parser/codegen 专门处理
（`emitMethodCall` 的方法名提取要兼容 IndexExpressionNode 形态）。
新设计 §1.4 提供了退路（"若实现困难可砍去 pool.new[T]"），
但砍去会让"非 var 位置构造"退回标签区——我建议**先实现标签区出生地**（无语法冲突），
`pool.new[T]` 作为第二步（有语法冲突但可控），若遇阻再启用 §1.4 退路。

### 1.3 与已实施部分的衔接

- L0-4（多类型标签冲突报错）与 §1.6 判定顺序一致：
  当前"两个能解析成具体类型的标签报错"需扩展为
  "类型标签 + 出生地标签可共存"，不能一味报错。这是**实施时必须改的一处**。
- L0-6（Pool 保留名）已挡住 `class Pool`，与 §1.1 一致。

## 2. §2 fill/clear/release —— 语义闭环，方法与状态格需新做

### 2.1 语义裁决状态：✅ 完整

- 调用形态确定为方法：`p.fill(c)` / `p.clear()` / `pool.release(x)`。
- `release` 的 x 是槽位引用；只对自定义 Pool 出生地的 Body 可用，跨池报错；
  默认出生地的 Body 不能 release（语法上天然挡住）；`clear` 与出生地无关。
- §2.2 明确：E/F/H/X 四态是**编译期事实表**，不是 ABI 变更。
- §2.4 明确状态与子引用在同一事实表，交叉依赖已对齐。

### 2.2 与现有语法的冲突

| 探针 | 当前结果 | 冲突性质 |
|---|---|---|
| `p.fill(c)` | `Class Player has no method named 'fill'` | 预期：方法未实现；语法本身能解析 |
| `p.clear()` | 同上 | 同上 |
| `pool.release(x)` | `Cannot determine the object type of method call` | 需 Pool 类型先落地 |

**结论**：无语法形态冲突（都是标准方法调用），只需在 `emitMethodCall` 里
仿照 ref/mut/take 的模式加内建方法 + 事实表。

### 2.3 与已实施部分的衔接

- 当前 `_moveStates` 是 `vector<map<string,bool>>`（F/X 两态），
  §2.2 要求扩展为四态事实表（E/F/H/X）。这是**编译器内部表示变更**，
  已在 §2.2 明确"不是 ABI 变更"，无需用户批准。
- `take` 落定（已实施）写的是 moved=true，需迁移到新事实表的 X 态。

## 3. §3 take 挂起态与独占检查 —— 语义闭环，是当前实现的最大差距

### 3.1 语义裁决状态：✅ 完整

- 挂起态 = 事实表的 `pending_take` 集合（语句作用域临时事实），不是事务、不是运行时元数据。
- "同一语句" = 同一 AST 语句节点；分号/换行算不同语句。
- 独立 take 语句 → 编译警告，走现有诊断机制。
- `throw` 时挂起态不回填，body 变 `?`。

### 3.2 与当前实现的差距（**关键**）

当前实现（提交 60d4cf6）是"take 本身不标记，只在落定位置标记"——
**绕过了挂起态**。后果：
- "同一语句二次 take 报错"未实现
- "挂起期间不能 fill/clear/release"未实现
- "挂起期间允许通过引用读、直接读写字段"未实现（但保持 F 恰好等价允许）
- 独立 take 语句的警告未实现

§3.1 明确 `pending_take` 是**编译期事实表的临时维度**，
所以补齐它不需要 ABI 变更，但需要语句级结算点
（`emitStatement` 末统一清空 pending_take）。这是可行的实施路径。

## 4. §4 子引用/NLL —— 语义闭环，实现细节划给实施侧

### 4.1 语义裁决状态：✅ 完整

- 路径穿透引用展开（按 `from` 展开）、跨函数缺 `from` 退 `⊤`。
- 过程内 NLL + 跨函数签名标注保守。
- `split/get_mut` 路径登记、不等事实 `i≠j`。
- §4.4 明确路径编码是实现细节。

### 4.2 与当前实现的差距

当前 `&p.name` 明确报 L3 诊断（不支持子引用）。§4 落地需：
- 新事实表维度：路径字符串 + 活跃引用集合 + 不等事实
- NLL 数据流分析（过程内）
- `emitStatement`/函数出口的活跃集合结算

这是一块独立的大工程，建议在 §1–§3 完成后再做。
